# 运维操作说明书

> 适用：又见炊烟餐饮管理系统 2.0  
> 部署形态：Docker 四容器（MySQL / RabbitMQ / Backend / Frontend）  
> 维护：地龙（DL-BOT）  
> 更新：2026-08-02

---

## 1. 系统架构概览

又见炊烟餐饮管理系统 2.0 采用前后端分离架构，整体基于 Docker 容器化部署。前端基于 Vue 3.4 + Vite 5 构建，由 Nginx 反向代理承载静态资源并转发接口请求；后端基于 Spring Boot 3.2.5 + Java 17 实现，提供 51 个 Controller 的 RESTful 接口；数据持久化采用 MySQL 8.0；异步通知采用 RabbitMQ 3.13。

系统采用多租户隔离设计，所有业务表强制携带 `store_id` 字段，通过 `StoreDataScopeAspect` AOP 切面在查询时自动注入数据范围，在写入时由 Controller 调用 `UserContext.assertStoreAccess(targetStoreId)` 进行越权断言。当前接入两家门店：宁国店（store_id=1）、宣城店（store_id=2）。

请求处理链路为：客户端请求 → Nginx（80/443）→ EncodingFilter（UTF-8 强制编码）→ CorsFilter（跨域）→ JwtAuthInterceptor（鉴权并注入 UserContext）→ RateLimitInterceptor（限流）→ StoreDataScopeAspect（门店数据范围）→ Controller → Service（事务）→ Repository → MySQL → AuditLogAspect（REQUIRES_NEW 独立事务记录审计日志）→ NotifyPublisher（同步落库 + MQ 异步推送）→ GlobalExceptionHandler（异常兜底）→ 返回 `Result<T>`。

后端具备降级能力：当 `app.notify.enabled=false`（默认）时，无 RabbitMQ 也能启动；生产者始终同步落库兜底，MQ 发送失败仅记录日志，不阻断主流程。这使得系统在 MQ 故障时仍能保证业务连续性。

## 2. 部署架构

系统通过 `youjian-docker/docker-compose.yml` 编排四个核心容器，容器之间通过 Docker 内部网络通信，仅前端容器对外暴露端口。

| 服务 | 容器名 | 镜像 | 端口 | 依赖 | 数据卷 |
|------|--------|------|------|------|--------|
| mysql | youjian-mysql | mysql:8.0 | 3306 | - | mysql-data |
| rabbitmq | youjian-rabbitmq | rabbitmq:3.13-management-alpine | 5672/15672 | - | rabbitmq-data |
| backend | youjian-backend | 自构建（OpenJDK 17） | 8080 | mysql healthy + rabbitmq started | app-logs |
| frontend | youjian-frontend | nginx:alpine | 80 | backend | - |

网络拓扑：外部流量经由 80/443 端口进入 `youjian-frontend`（Nginx），静态资源由 Vue 直接返回，`/api/*` 请求通过 `proxy_pass` 转发至 `youjian-backend:8080`，`/ws/*` 转发至 WebSocket。后端容器访问 `youjian-mysql:3306` 与 `youjian-rabbitmq:5672`，并可通过外网访问腾讯云 COS 与短信通道。

数据库初始化 SQL 存放在 `youjian-docker/mysql/init/` 目录下，包含 `banquet_init.sql`（业务表 DDL）与 `rbac_init.sql`（RBAC 表 DDL），首次启动时自动执行。增量迁移 SQL 存放在 `banquet_project/src/main/resources/` 与 `scripts/migrations/` 目录，需手动执行。

环境变量统一通过 `youjian-docker/.env` 文件管理（被 .gitignore 忽略），包含 MySQL 凭据、JWT 密钥、AES 密钥、RabbitMQ 凭据、COS 凭据等敏感配置。所有密钥建议使用 `openssl rand -base64 48` 生成 48 位以上随机字符串。

## 3. 日常运维操作

### 3.1 启动

首次部署或全量启动：
```bash
cd youjian-docker
cp .env.example .env   # 首次需要编辑填入密钥
docker compose up -d
```

仅启动（容器已存在，已停止）：
```bash
docker compose start
```

按依赖顺序启动：
```bash
docker compose up -d mysql rabbitmq
docker compose up -d backend
docker compose up -d frontend
```

启动后验证：
```bash
docker compose ps                              # 查看容器状态
curl http://localhost:8080/actuator/health     # 后端健康检查
curl http://localhost/                         # 前端首页
```

### 3.2 停止

优雅停止（保留容器与数据卷）：
```bash
docker compose stop
```

停止并删除容器（保留数据卷）：
```bash
docker compose down
```

停止并删除容器与数据卷（危险，全部数据丢失）：
```bash
docker compose down -v
```

### 3.3 重启

重启全部服务：
```bash
docker compose restart
```

重启单个服务（如后端代码热更新后）：
```bash
docker compose restart backend
```

重新构建并启动后端（代码变更后）：
```bash
docker compose build backend
docker compose up -d backend
```

### 3.4 备份

数据库手动备份（业务低峰期执行）：
```bash
docker exec youjian-mysql mysqldump \
  -uroot -p$MYSQL_ROOT_PASSWORD \
  --single-transaction --routines --triggers \
  banquet > backup_$(date +%Y%m%d_%H%M%S).sql
```

压缩备份（节省空间）：
```bash
docker exec youjian-mysql mysqldump -uroot -p$MYSQL_ROOT_PASSWORD \
  --single-transaction banquet | gzip > /backup/banquet_$(date +%Y%m%d).sql.gz
```

上传至腾讯云 COS：
```bash
python scripts/backup/cos_upload.py --file backup_20260802.sql
```
凭据自动从 `~/.cos.conf` 读取。

### 3.5 恢复

从压缩备份恢复：
```bash
gunzip < backup_20260802.sql.gz | \
  docker exec -i youjian-mysql mysql -uroot -p$MYSQL_ROOT_PASSWORD banquet
```

从普通 SQL 备份恢复：
```bash
docker exec -i youjian-mysql mysql -uroot -p$MYSQL_ROOT_PASSWORD banquet < backup_20260802.sql
```

恢复前必须停止后端容器，避免恢复期间产生新写入：
```bash
docker compose stop backend
# 执行恢复
docker compose start backend
```

## 4. 日志查看

### 4.1 日志文件分类

后端日志由 `logback-spring.xml` 配置，按用途分文件输出，存放于 `app-logs` 数据卷（容器内 `/app/logs`）：

| 日志文件 | 内容 | 轮转策略 |
|---------|------|---------|
| app.log | 应用主日志（INFO 及以上） | 按天滚动，保留 30 天 |
| auth.log | 鉴权日志（登录/登出/Token 刷新/越权访问） | 按天滚动，保留 90 天 |
| error.log | 错误日志（ERROR 级别，含堆栈） | 按天滚动，保留 90 天 |
| access.log | 接口访问日志（可选开启） | 按天滚动，保留 7 天 |

### 4.2 查看容器日志

实时跟踪后端日志：
```bash
docker compose logs -f backend
```

查看最近 200 行：
```bash
docker compose logs --tail=200 backend
```

按时间段查看：
```bash
docker compose logs --since="2026-08-02T00:00:00" --until="2026-08-02T06:00:00" backend
```

### 4.3 查看日志文件

进入容器查看日志文件：
```bash
docker exec -it youjian-backend sh
cd /app/logs
tail -f app.log
grep "ERROR" error.log | tail -50
```

从宿主机直接读取：
```bash
docker exec youjian-backend cat /app/logs/error.log | grep -A 20 "NullPointerException"
```

### 4.4 鉴权日志分析

鉴权日志记录所有认证相关事件，是安全审计的关键依据。常见排查场景：

- 登录失败排查：`grep "LOGIN_FAIL" /app/logs/auth.log | tail -50`
- Token 失效统计：`grep "TOKEN_EXPIRED" /app/logs/auth.log | wc -l`
- 越权访问告警：`grep "ACCESS_DENIED" /app/logs/auth.log`
- 暴力破解识别：连续多次 `LOGIN_FAIL` 且同一 IP，触发 `RateLimitInterceptor` 限流。

### 4.5 错误日志排查

`error.log` 记录所有未捕获异常与显式抛出的业务错误。排查时优先关注：

- `NullPointerException`：通常为参数校验缺失，需定位具体 Controller。
- `DataIntegrityViolationException`：数据库约束冲突，检查外键或唯一索引。
- `OptimisticLockingFailureException`：乐观锁冲突，并发更新同一记录。
- `ConnectTimeoutException`：外部依赖（MySQL/RabbitMQ/COS）不可达。

### 5.1 Actuator 健康检查

后端集成 Spring Boot Actuator，提供健康检查与信息查询端点：

```bash
# 健康状态（返回 {"status":"UP"}）
curl http://localhost:8080/actuator/health

# 健康详情（含数据库、MQ、磁盘等组件状态）
curl http://localhost:8080/actuator/health/details

# 应用信息

# 指标（JVM、HTTP 请求等）
curl http://localhost:8080/actuator/metrics

curl http://localhost:8080/actuator/metrics/http.server.requests
```

生产环境建议通过外部监控（如 Prometheus + Grafana）周期性抓取 `/actuator/prometheus`，设置告警阈值。

### 5.2 容器资源监控

实时监控容器 CPU、内存、网络、IO：
```bash
docker stats
```

输出示例：
```
CONTAINER           CPU %   MEM USAGE / LIMIT   MEM %   NET I/O
youjian-backend     12.5%   512MiB / 2GiB       25.0%   1.2GB/800MB

youjian-rabbitmq    2.1%    128MiB / 1GiB       12.5%   50MB/60MB
youjian-frontend    0.5%    24MiB / 512MiB      4.7%    2GB/1.5GB
```

### 5.3 数据库监控

MySQL 连接数与慢查询：
```bash
docker exec youjian-mysql mysql -uroot -p -e "
  SHOW STATUS LIKE 'Threads_connected';
  SHOW STATUS LIKE 'Slow_queries';
  SHOW PROCESSLIST;
"
```

HikariCP 连接池状态（通过 Actuator）：
```bash
curl http://localhost:8080/actuator/metrics/hikaricp.connections.active
curl http://localhost:8080/actuator/metrics/hikaricp.connections.pending
```
当 `connections.pending` 持续大于 0，说明连接池不足，需调大 `spring.datasource.hikari.maximum-pool-size`。

### 5.4 RabbitMQ 监控

管理台地址：http://localhost:15672 ，账号密码见 `.env`。重点观察：

- Queues → `youjian.notify.queue` 消息堆积（`Ready` 与 `Unacked` 数量）
- Exchanges → `youjian.notify.exchange` 流量
- Connections / Channels 连接数

当 `Ready` 持续增长，说明消费者 `NotifyConsumer` 处理速度跟不上，需检查后端日志是否有消费异常。

### 5.5 告警阈值建议

| 指标 | 告警阈值 | 紧急阈值 |
|------|---------|---------|
| 后端 CPU | > 70% 持续 5 分钟 | > 90% |
| 后端内存 | > 80% | > 95% |
| MySQL 连接数 | > 80% 最大连接 | = 最大连接 |
| RabbitMQ 队列堆积 | > 1000 条 | > 10000 条 |
| 接口 P99 响应 | > 2 秒 | > 5 秒 |
| 磁盘使用 | > 80% | > 90% |

## 6. 常见故障排查

### 6.1 端口占用

现象：容器启动失败，日志报 `Bind address already in use`。

排查：
```bash
netstat -ano | findstr :8080      # Windows
lsof -i:8080                       # Linux
```

处理：释放被占用端口，或修改 `docker-compose.yml` 中端口映射（如 `8081:8080`）。常见冲突端口：80（前端）、8080（后端）、3306（MySQL）、15672（RabbitMQ 管理台）。

### 6.2 数据库连接失败

现象：后端启动报 `Communications link failure` 或 `Access denied`。

排查步骤：
```bash
# 1. 检查 MySQL 容器状态
docker compose ps mysql
docker compose logs mysql

# 2. 测试 MySQL 连接
docker exec youjian-mysql mysql -uroot -p$MYSQL_ROOT_PASSWORD -e "SELECT 1;"

# 3. 检查后端配置
docker exec youjian-backend env | grep MYSQL
```

常见原因：
- MySQL 容器未健康就绪：`docker-compose.yml` 已配置 `healthcheck` 与 `depends_on: condition: service_healthy`，若仍失败可手动等待后重启后端。
- 密码不匹配：`.env` 中 `MYSQL_PASSWORD` 与 `MYSQL_ROOT_PASSWORD` 必须与 MySQL 容器初始化时一致。若初始化后修改密码，需进入 MySQL 执行 `ALTER USER`。
- 网络隔离：确认后端与 MySQL 在同一 Docker 网络（默认 `youjian_default`）。

### 6.3 RabbitMQ 不可达

现象：后端日志报 `AmqpConnectException`，但业务仍可正常进行（降级机制生效）。

排查：
```bash
docker exec youjian-rabbitmq rabbitmqctl status
docker exec youjian-rabbitmq rabbitmqctl list_queues
```

处理：
- 若 `NOTIFY_ENABLED=false`，属正常降级，不影响业务。
- 若 `NOTIFY_ENABLED=true`，检查 `.env` 中 `RABBITMQ_USER`/`RABBITMQ_PASSWORD` 与容器 `RABBITMQ_DEFAULT_USER`/`RABBITMQ_DEFAULT_PASS` 是否一致。
- 重启 RabbitMQ：`docker compose restart rabbitmq`，随后重启后端重建连接。

### 6.4 JWT 失效

现象：前端报 401 Unauthorized，接口返回 `Token 已过期`或`无效的 Token`。

排查：
```bash
# 查看鉴权日志
docker exec youjian-backend grep "TOKEN" /app/logs/auth.log | tail -20
```

常见原因：
- Token 过期：默认有效期由 `app.jwt.expire-minutes` 配置，前端需调用刷新接口。
- `JWT_SECRET` 变更：重启后端后所有旧 Token 失效，需用户重新登录。
- 客户端时间偏差：若客户端时间与服务端相差过大，可能误判过期。

处理：让用户重新登录；若大面积失效，检查 `JWT_SECRET` 是否被误改。

### 6.5 前端 502/504

现象：浏览器访问前端报 502 Bad Gateway 或 504 Gateway Timeout。

排查：
```bash
docker compose logs frontend              # Nginx 日志
docker compose logs --tail=50 backend     # 后端是否存活
curl http://localhost:8080/actuator/health
```

处理：通常为后端未启动或崩溃。重启后端：`docker compose restart backend`；若后端无法启动，按 6.2 排查数据库连接。

### 6.6 数据库锁等待

现象：接口响应极慢，日志报 `Lock wait timeout exceeded`。

排查：
```bash
docker exec youjian-mysql mysql -uroot -p -e "
  SELECT * FROM information_schema.INNODB_TRX;
  SELECT * FROM information_schema.INNODB_LOCKS;
  SELECT * FROM information_schema.INNODB_LOCK_WAITS;
"
```

处理：定位长时间未提交的事务（`trx_started` 较早的记录），必要时 `KILL <线程ID>`。根本解决需排查 Service 层长事务，确保事务边界最小化。

## 7. 数据备份策略

### 7.1 备份策略总览

系统采用"每日全量 + binlog 增量"的双重备份策略，保证数据可恢复到任意时间点。

| 备份类型 | 频率 | 保留期 | 存储位置 | 用途 |
|---------|------|--------|---------|------|
| 全量备份 | 每日 03:00 | 30 天 | 本地 + COS | 整库恢复 |
| binlog 增量 | 实时 | 7 天 | 本地 | 时间点恢复 |
| 周备份 | 每周日 02:00 | 90 天 | COS | 长期归档 |

### 7.2 全量备份

通过 cron 定时任务（每日凌晨 3 点）：
```bash
# 编辑 crontab
crontab -e

# 添加定时任务
0 3 * * * docker exec youjian-mysql mysqldump -uroot -p$MYSQL_ROOT_PASSWORD \
  --single-transaction --routines --triggers --flush-logs \
  banquet | gzip > /backup/banquet_$(date +\%Y\%m\%d).sql.gz && \
  python /opt/youjian/scripts/backup/cos_upload.py --file /backup/banquet_$(date +\%Y\%m\%d).sql.gz
```

`--single-transaction` 保证 InnoDB 一致性快照，不锁表；`--flush-logs` 切换 binlog，便于增量备份定位。

### 7.3 binlog 增量备份

启用 MySQL binlog（`my.cnf` 中 `log-bin=mysql-bin`、`binlog_format=ROW`）后，所有数据变更记录在 binlog 中。

定期归档 binlog：
```bash
docker exec youjian-mysql mysql -uroot -p -e "FLUSH LOGS;"
docker cp youjian-mysql:/var/lib/mysql/mysql-bin.0000X /backup/binlog/
```

### 7.4 时间点恢复（PITR）

目标：将数据库恢复到 2026-08-02 14:30:00 的状态。

```bash
# 1. 恢复最近的全量备份（8/2 凌晨 3 点）
gunzip < /backup/banquet_20260802.sql.gz | \
  docker exec -i youjian-mysql mysql -uroot -p$MYSQL_ROOT_PASSWORD banquet

# 2. 应用 binlog 到目标时间点
docker exec -i youjian-mysql mysqlbinlog --start-datetime="2026-08-02 03:00:00" \
  --stop-datetime="2026-08-02 14:30:00" \
  /var/lib/mysql/mysql-bin.0000X | \
  docker exec -i youjian-mysql mysql -uroot -p$MYSQL_ROOT_PASSWORD banquet
```

### 7.5 备份验证

每周执行一次恢复演练，验证备份有效性：
```bash
# 在测试环境恢复
docker run -d --name verify-mysql -e MYSQL_ROOT_PASSWORD=test mysql:8.0
gunzip < /backup/banquet_20260802.sql.gz | \
  docker exec -i verify-mysql mysql -uroot -ptest -e "CREATE DATABASE banquet; USE banquet; SOURCE /dev/stdin;"
# 校验关键表行数
docker exec verify-mysql mysql -uroot -ptest banquet -e "
  SELECT COUNT(*) FROM staff_master WHERE is_active=1;
  SELECT COUNT(*) FROM booking_master;
  SELECT COUNT(*) FROM finance_voucher;
"
```

### 7.6 备份清理

避免磁盘被旧备份撑满：
```bash
# 清理 30 天前的全量备份
find /backup -name "banquet_*.sql.gz" -mtime +30 -delete
# 清理 7 天前的 binlog
find /backup/binlog -name "mysql-bin.*" -mtime +7 -delete
```

## 8. 安全审计

### 8.1 审计日志体系

系统具备完整的审计留痕能力，所有敏感操作均记录日志：

| 日志类型 | 存储位置 | 记录内容 | 保留期 |
|---------|---------|---------|--------|
| 操作日志 | audit_log 表 + app.log | 增删改业务操作 | 永久 |
| 登录日志 | auth.log | 登录/登出/Token 刷新 | 90 天 |
| 数据变更日志 | change_log 表 | 关键字段前后值 | 永久 |
| 审批日志 | approval_log 表 | 审批操作（同意/驳回/撤销） | 永久 |

### 8.2 操作日志（audit_log）

通过 `AuditLogAspect` AOP 切面自动记录，使用 `REQUIRES_NEW` 独立事务，确保即使主业务事务回滚，审计日志仍留存。

记录字段：操作人 ID、操作人姓名、操作时间、操作类型（CREATE/UPDATE/DELETE）、模块、目标对象 ID、请求参数、IP 地址、User-Agent、执行结果、耗时。

查询操作日志：
```sql
-- 查询某用户近 7 天的操作
SELECT * FROM audit_log
WHERE operator_id = ?
  AND created_at >= DATE_SUB(NOW(), INTERVAL 7 DAY)
ORDER BY created_at DESC;

-- 查询某模块的删除操作
SELECT * FROM audit_log
WHERE operation_type = 'DELETE'
  AND module = 'finance_voucher'
ORDER BY created_at DESC;
```

### 8.3 登录日志

`auth.log` 记录所有认证事件，包括登录成功、登录失败（错误密码）、Token 刷新、Token 过期、越权访问。登录失败连续 5 次将触发账户锁定（由 `RateLimitInterceptor` 与业务逻辑共同实现）。

### 8.4 敏感数据保护

- 身份证号、银行卡号通过 `AESUtil` 加密存储，密钥由环境变量 `AES_SECRET_KEY` 注入。
- 接口返回时通过 `SensitiveDataSerializer` / `IdCardSerializer` 自动脱敏（如身份证显示为 `340***********1234`）。
- 严禁在日志中打印完整身份证、银行卡、密码等敏感信息。

### 8.5 审计报表

定期生成审计报表，提交管理层审阅：
- 每日：登录异常、越权访问、删除操作清单。
- 每周：高权限账号（管理员、老板）操作汇总。
- 每月：全量操作统计、敏感数据访问统计。

### 8.6 角色权限管理

系统采用 RBAC（基于角色的访问控制）模型，通过五张表实现权限体系：`sys_role`（角色）、`sys_user_role`（用户角色关联）、`sys_role_permission`（角色权限关联）、`sys_permission`（权限点）、`sys_menu`（菜单）。当前预设九个角色：管理员、老板、店长、服务员、厨师长、收银员、财务、采购、库管，覆盖前厅、后厨、采购仓储、财务、人事等全部业务岗位。

权限分为三类：可见可操作（√）、只读（△）、无权限（×）。各角色按岗位职责分配权限，遵循最小权限原则。管理员拥有全部权限；店长负责本店经营与人员管理；服务员仅具备预订与桌台基础操作；厨师长聚焦厨房与菜品；收银员负责结账与账单；财务掌管凭证与对账；采购与库管分别负责采购申请与库存收发。

新增或调整角色权限时，须按规范执行 SQL：先插入 `sys_role` 定义角色，再批量插入 `sys_role_permission` 关联权限点，最后通过 `sys_user_role` 分配给用户。所有权限变更必须留痕，并在测试环境验证后再同步生产。详细的角色菜单对照关系见同目录 `05_权限审批流/角色-权限-菜单对照表.xlsx`。

### 8.7 安全加固清单

生产环境安全加固是运维的常态化工作，须逐项落实：

- 端口隔离：MySQL（3306）与 RabbitMQ（5672/15672）严禁对公网开放，仅允许 Docker 内部网络访问；仅前端 Nginx 的 80/443 端口对外。
- 强密码策略：所有凭据（数据库、MQ、JWT、AES）均使用 48 位以上随机字符串，通过 `openssl rand` 生成，禁止使用弱口令。
- 密钥轮换：JWT 密钥与 AES 密钥建议每季度轮换一次，轮换前通知全员重新登录。
- Swagger 关闭：生产环境设置 `springdoc.swagger-ui.enabled=false`，避免接口结构泄露。
- HTTPS 强制：Nginx 配置 SSL 证书并开启 HSTS，所有 HTTP 请求 301 跳转至 HTTPS。
- 日志脱敏：确保 `logback-spring.xml` 中不输出完整身份证、银行卡、手机号等敏感字段。
- 依赖扫描：定期检查第三方依赖（Spring Boot、MySQL 驱动等）是否存在已知漏洞，及时升级补丁版本。
- 防火墙规则：服务器仅放行业务必需端口（80/443/22），SSH 端口建议修改默认值并限制来源 IP。

## 9. 升级流程

### 9.1 蓝绿部署概述

系统采用蓝绿部署策略，保证升级期间业务零中断。蓝绿两组环境同时存在，通过 Nginx upstream 切换流量。

```
                 ┌─────────────────┐
   流量 ────────▶│  Nginx (active) │
                 └────────┬────────┘
                          │
              ┌───────────┴───────────┐
              ▼                       ▼
     ┌─────────────────┐     ┌─────────────────┐
     │  蓝环境(当前)    │     │  绿环境(待发布) │
     │  backend-blue   │     │  backend-green  │
     │  :8080          │     │  :8081          │
     └─────────────────┘     └─────────────────┘
              │                       │
              └───────────┬───────────┘
                          ▼
                  ┌──────────────┐
                  │  MySQL(共享) │
                  │  RabbitMQ    │
                  └──────────────┘
```

### 9.2 升级步骤

1. **准备绿环境**：构建新镜像并启动绿环境容器（端口 8081），连接同一 MySQL/RabbitMQ。
   ```bash
   docker compose -f docker-compose.green.yml build backend
   docker compose -f docker-compose.green.yml up -d backend
   ```

2. **健康验证**：对绿环境执行健康检查与冒烟测试。
   ```bash
   curl http://localhost:8081/actuator/health
   # 执行冒烟测试用例（见 100 场景测试用例）
   ```

3. **切换流量**：修改 Nginx upstream 指向绿环境，reload Nginx。
   ```bash
   # 修改 nginx.conf 中 proxy_pass 为 backend-green:8081
   docker exec youjian-frontend nginx -s reload
   ```

4. **观察**：保持蓝环境运行 30 分钟，观察绿环境日志与监控指标。若异常立即切回蓝环境。

5. **清理**：确认稳定后停止并移除蓝环境，将绿环境重命名为新的蓝环境。
   ```bash
   docker compose -f docker-compose.blue.yml down
   ```

6. **数据库迁移**：若升级含 DDL 变更，在切换流量前执行增量 SQL（确保向后兼容，先执行 DDL 再发布代码）。

### 9.3 回滚

若升级后发现严重问题，执行回滚：

1. 切换 Nginx 回蓝环境：`docker exec youjian-frontend nginx -s reload`。
2. 若已执行数据库迁移，回滚 SQL：
   ```bash
   docker exec -i youjian-mysql mysql -uroot -p$MYSQL_ROOT_PASSWORD banquet < rollback_xxx.sql
   ```
3. 通知用户并记录回滚原因，复盘后重新发布。

### 9.4 数据库迁移规范

- DDL 变更必须先于代码发布执行（向后兼容）。
- 禁止 `ALTER TABLE` 大表（百万行）直接执行，需使用 `pt-online-schema-change`。
- 每次 migration SQL 必须配套编写 rollback SQL。
- 迁移前必须备份：`mysqldump` 全量备份。

## 10. 应急处理

### 10.1 数据库主从切换

当前为单库部署，规划主从架构后，主库故障需切换从库：

1. **确认主库故障**：`docker exec youjian-mysql mysqladmin ping` 失败，或日志报 `InnoDB: Database page corruption`。
2. **提升从库为主**：
   ```bash
   docker exec youjian-mysql-slave mysql -uroot -p -e "
     STOP SLAVE;
     RESET SLAVE ALL;
     SET GLOBAL read_only=OFF;
   "
   ```
3. **修改后端配置**：`.env` 中 `MYSQL_HOST` 指向新主库，重启后端。
4. **通知业务**：通过站内通知告知店长，确认业务恢复。
5. **修复旧主库**：从新主库重新搭建从库，恢复高可用。

### 10.2 数据库回滚

误操作（如误删数据、错误更新）后的应急回滚：

1. **立即停止后端**，防止新写入覆盖 binlog。
2. **定位误操作时间点**：通过 `audit_log` 或 `change_log` 确认误操作发生时间。
3. **执行时间点恢复**（见 7.4）：在测试库恢复到误操作前，导出受影响表数据，再回灌生产库。
4. **验证数据一致性**：核对关键表行数、金额字段。
5. **重启后端**，通知业务方。

### 10.3 RabbitMQ 故障

RabbitMQ 宕机时，系统自动降级（`NotifyPublisher` 同步落库兜底），通知功能暂停但不影响主业务。处理：

```bash
docker compose restart rabbitmq
docker compose restart backend   # 重建 MQ 连接
```

若 RabbitMQ 数据损坏，清理数据卷重建：
```bash
docker compose down rabbitmq
docker volume rm youjian_rabbitmq-data
docker compose up -d rabbitmq
```

### 10.4 后端 OOM / 崩溃

现象：后端容器退出，`docker compose ps` 显示 `Exited (137)`（OOM 被 kill）。

处理：
```bash
# 查看容器退出原因
docker inspect youjian-backend | grep -A 5 "OOMKilled"
# 调大内存限制（docker-compose.yml）
#   deploy:
#     resources:
#       limits:
#         memory: 4G
docker compose up -d backend
```

同时分析堆内存：导出 heap dump 供开发分析，检查是否存在内存泄漏（如未关闭的 JPA EntityManager、缓存无限增长）。

### 10.5 磁盘告警

日志或备份撑满磁盘会导致 MySQL 崩溃、后端无法写日志。应急：

```bash
# 1. 查看磁盘占用
df -h
# 2. 定位大文件
du -sh /var/lib/docker/volumes/* | sort -rh | head
# 3. 清理旧日志与备份
docker exec youjian-backend find /app/logs -name "*.log" -mtime +30 -delete
find /backup -name "banquet_*.sql.gz" -mtime +7 -delete
# 4. 清理 Docker 无用镜像
docker system prune -a
```
