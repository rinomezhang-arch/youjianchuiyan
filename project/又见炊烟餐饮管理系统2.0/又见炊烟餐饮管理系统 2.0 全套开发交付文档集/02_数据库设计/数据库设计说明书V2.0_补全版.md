# 数据库设计说明书 V2.0（补全版）

> 版本：V2.0 补全版  
> 更新日期：2026-08-02  
> 适用：MySQL 8.0 + utf8mb4 + InnoDB  
> 数据库：banquet  
> 维护：地龙（DL-BOT）

---

## 1. 设计原则

本系统面向「又见炊烟」多门店餐饮集团（宁国店、宣城店）的一体化运营，数据库设计在满足业务功能的前提下，重点强化多租户隔离、数据安全、金额精度与可审计性。核心设计原则如下：

### 1.1 多租户隔离

全表通过 `store_id BIGINT NOT NULL` 字段实现门店级数据隔离，约定 `0=全局共享`（如字典、系统配置默认值、超级总经理数据）、`1=宁国店`、`2=宣城店`。所有业务查询强制携带 `WHERE store_id = ?` 条件，写入侧由后端 `UserContext.getCurrentStoreId()` 注入当前门店，禁止前端直接传入 `storeId` 以防越权伪造。仅 `data_scope = all` 的超级总经理（GM）角色可跨门店查询与汇总。该机制保证店长、服务员、厨师长等角色只能看到本店数据，从物理层面杜绝跨店数据泄露。

### 1.2 逻辑删除

全表采用逻辑删除策略，通过 `is_deleted TINYINT NOT NULL DEFAULT 0`（部分表使用 `is_active TINYINT DEFAULT 1` 启停标志）标识记录是否已被删除。删除操作仅将标志位置 1，不物理清除数据，所有查询默认追加 `is_deleted = 0` 过滤。该策略保障客户档案、预订单、财务凭证等关键业务数据可追溯、可恢复，满足财务审计与纠纷回查需求。物理删除仅在数据归档清理场景由 DBA 人工执行。

### 1.3 金额精度

系统禁止使用 FLOAT/DOUBLE 存储金额，全表金额字段统一使用 `DECIMAL(12,2)`，整数位 10 位、小数 2 位，可承载最大 99,999,999,999.99 的金额值，完全覆盖单店年度营收与单笔大额宴会订单。比例、百分比、折扣率使用 `DECIMAL(10,2)`；数量字段（支持 0.5 斤等小数）使用 `DECIMAL(10,2)`。该规范避免浮点运算导致的精度丢失，确保财务对账、成本核算、积分计算的精确性。

### 1.4 审计日志

系统建立多层级审计体系：`audit_logs` 记录接口级操作审计（操作人、IP、URL、方法、耗时、结果），`change_log` 记录关键字段变更前后值（数据级审计），`sys_operation_log` 记录后台操作日志，`approval_log` 记录审批流转轨迹，`kitchen_log` 记录后厨出菜日志。所有审计表均带 `store_id` 与时间戳，支持按门店、按时间、按操作人检索，满足内控合规与问题排查需求。

### 1.5 其它原则

字符集统一 `utf8mb4`（支持 emoji 与生僻字），排序规则 `utf8mb4_unicode_ci`（部分历史表 `utf8mb4_0900_ai_ci`）；存储引擎统一 `InnoDB` 支持事务与行级锁；所有表均设自增整型主键；时间字段使用 `timestamp`/`datetime` 默认 `CURRENT_TIMESTAMP`，更新时间带 `ON UPDATE CURRENT_TIMESTAMP`。

## 2. 命名规范

| 对象 | 规范 | 示例 |
|------|------|------|
| 数据库 | 小写英文单词 | banquet |
| 表名 | 蛇形小写，模块前缀 + 业务名 | booking_master、finance_account、tool_master |
| 字段名 | 蛇形小写 | store_id、created_at、is_deleted |
| 主键 | 表名去前缀 _id 或 id | staff_id、booking_id、id |
| 外键 | 引用表主键名 + 当前语境 | supplier_id、booking_master_id |
| 索引 | idx_ 字段名；唯一索引 uk_ 字段名 | idx_store_status、uk_booking_no |
| 外键约束 | fk_ 当前表缩写 _ 引用表 | fk_booking_master、fk_ar_staff |
| 状态字段 | varchar(20) 字典编码 或 tinyint | status='active'、is_deleted=0 |
| 时间字段 | _at / _time 后缀 | created_at、approve_time |

表名前缀约定：`booking_` 预订、`dish_` 菜品、`finance_` 财务、`stock_` 库存、`purchase_` 采购、`tool_` 工具、`marketing_` 营销、`member_` 会员、`report_` 报表、`sys_` 系统、`approval_` 审批、`engineering_`/`maintenance_`/`energy_`/`decoration_`/`floor_`/`safety_` 工程、`attendance_` 考勤、`schedule_` 排班。

## 4. 索引规范

- **主键**：所有表必须有 AUTO_INCREMENT 整型主键，聚簇索引。
- **唯一索引**：业务编码字段强制唯一，如 `uk_booking_no(booking_no)`、`uk_role_code(role_code)`、`uk_staff_account(staff_account)`、`uk_ingredient_code(ingredient_code)`、`uk_supplier_code(supplier_code)`、`uk_flow_no(flow_no)`、`uk_request_no(request_no)`。
- **复合索引**：覆盖 `store_id` + 业务字段，如 `idx_store_status(store_id,status)`、`idx_business(business_id,business_type)`，避免回表与全表扫描。
- **外键索引**：所有外键字段自动加索引，如 `idx_node_flow(flow_id)`、`idx_ur_staff(staff_id)`。
- **前缀索引**：长文本字段（如 URL）使用前缀索引控制体积。
- **避免过度索引**：单表索引数量控制在 6 个以内，写多读少表慎建索引。

## 7. 表间关系说明

### 7.1 核心主从关系

- `booking_master(1) -> booking_table(N)`：一场宴会预订占用多张桌位，外键 `fk_booking_master`，`ON DELETE RESTRICT` 防止误删主单遗留孤儿明细。
- `booking_master(1) -> booking_dish_detail(N)`：一场预订关联多道菜品，按 `booking_id` 关联，`ON DELETE RESTRICT`。
- `staff_master(1) -> attendance_records(N)/leave_record(N)/overtime(N)`：员工档案为考勤、请假、加班的统一主档，外键 `fk_ar_staff`/`fk_lr_staff`/`fk_ot_staff`，均 `ON DELETE RESTRICT`。
- `dish_master(1) -> dish_recipe(N)`：菜品与其配方（食材耗用）一对多，复合外键 `(dish_id,store_id)`，`ON DELETE RESTRICT`。
- `ingredient_master(1) -> ingredient_inventory_log(N)/ingredient_purchase(N)`：食材主档驱动库存日志与采购明细，复合外键 `(ingredient_id,store_id)`。

### 7.2 审批流关系

- `approval_template(1) -> approval_flow(N)`：模板定义节点序列，发起审批时按模板实例化 `approval_flow`。
- `approval_flow(1) -> approval_node(N)`：一个审批流实例包含多个顺序节点，`node_order` 决定流转次序，每节点记录审批人、状态、意见、时间。
- `approval_flow.business_id` 反向关联具体业务单据（请假单 leave_record、加班单 overtime、采购单 procurement_request、报销单 reimbursement、报损单 stock_loss），通过 `flow_type` 区分业务类型。

### 7.3 采购-库存-财务链路

- 采购链：`procurement_request(申请) -> purchase_order(订单) -> purchase_receipt(入库) -> purchase_return(退货)`，各主表均带明细子表（`_detail` 后缀）。
- 库存链：`ingredient_master(主档) -> ingredient_inventory_log(流水) -> inventory_summary(汇总)`；`stock_take/stock_loss/stock_transfer` 完成盘点、报损、调拨闭环。
- 财务链：`finance_payable(应付) -> finance_payment_record(付款) -> finance_reconciliation(对账) -> finance_settlement(结算)`；`finance_voucher -> finance_voucher_detail` 实现会计凭证主从；`finance_transaction` 记录账户收支流水并关联 `finance_account`。

### 7.4 权限与多租户关系

- `sys_user(用户) <-> sys_role(角色) <-> sys_permission(权限) / sys_menu(菜单)`：用户通过 `sys_user_role` 关联角色，角色通过 `sys_role_permission` 关联权限点、通过 `sys_role_menu` 关联菜单。
- `sys_role.data_scope` 决定数据范围（all=跨店 / store=本店），与 `store_id` 配合实现多租户隔离。
- `sys_user.store_id` 与 `staff_master.store_id` 一致，登录后注入会话上下文，作为所有业务查询的隐式过滤条件。

### 7.5 菜品-套餐-宴会关系

- `dish_category(分类) -> dish_master(菜品)`：菜品归属分类。
- `dish_master -> dish_cost_card -> dish_cost_card_detail`：菜品成本卡由食材明细组成，`dish_recipe` 记录标准配方，`yield_rate_config`/`unit_conversion` 提供出品率与单位换算支撑成本核算。
- `package_master -> package_dish_detail`：套餐由多道菜品组合；`banquet_template -> template_dish_rel` 定义宴会模板的菜品组合，`banquet_template_rel` 关联模板与宴会类型。

### 7.6 工具管理关系

- `tool_category(分类) -> tool_master(台账)`：工具归属分类。
- `tool_master(1) -> tool_issue(领用)/tool_return(归还)/tool_damage(损坏)(N)`：工具全生命周期流转，`tool_inventory` 记录盘点结果，`available_qty` 随领用/归还/损坏动态增减。

### 7.7 工程能源关系

- `maintenance_request(报修工单)` 关联 `maintenance_asset(资产登记)`；`engineering_work_order/inspection/spare_part` 构成工程运维闭环；`energy_record` 记录能耗，`decoration_project/floor_project/safety_issue` 覆盖装修、楼层工程、安全管理。
