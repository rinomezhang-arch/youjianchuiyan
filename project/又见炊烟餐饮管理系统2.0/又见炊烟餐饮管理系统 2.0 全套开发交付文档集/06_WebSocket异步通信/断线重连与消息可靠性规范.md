## 文档目的

本规范针对餐饮后厨 KDS（Kitchen Display System）高可用消息保障要求制定。后厨场景对消息可靠性要求极高：订单漏推送会导致出菜延迟甚至漏菜，消息重复会导致重复出菜，消息乱序会导致出菜顺序混乱影响宴会上菜节奏。本规范定义"消息不丢、不重、不乱序"三大目标的实现方案，覆盖心跳、重连、重试、幂等、顺序、离线补偿、降级、监控、测试全链路。项目当前 RabbitMQ 集成已实现 NotifyConsumer/NotifyPublisher，但 WebSocket 推送为 TODO 状态，本规范作为该 TODO 落地的实施依据。

## 一、概述

### 1.1 业务场景

| 场景 | 消息类型 | 可靠性要求 | 延迟要求 |
|------|---------|-----------|---------|
| KDS 后厨新订单推送 | order.created | 不丢、不重、不乱序 | < 1 秒 |
| KDS 菜品状态变更 | dish.status_changed | 不丢、不重 | < 1 秒 |
| 订单结账通知 | order.settled | 不丢、不重 | < 2 秒 |
| 宴会流程节点通知 | banquet.node_changed | 不丢、顺序严格 | < 2 秒 |
| 站内系统通知 | system.notify | 不丢、不重 | < 5 秒 |

### 1.2 三大可靠性目标

| 目标 | 含义 | 实现手段 |
|------|------|---------|
| 不丢 | 消息必达，网络故障也能补投 | RabbitMQ 持久化 + 离线补偿 + DLQ |
| 不重 | 同一消息只处理一次 | messageId 幂等 + Redis 去重 |
| 不乱序 | 同一订单消息按发送顺序处理 | 单队列 FIFO + orderId 分区 |

### 1.3 架构链路

```text
业务系统 -> NotifyPublisher -> RabbitMQ Exchange(youjian.notify.exchange)
    -> Queue(youjian.notify.queue) -> NotifyConsumer
    -> WebSocket(STOMP) -> 前端(KDS看板/收银台/宴会管理)

Exchange: youjian.notify.exchange
Queue:    youjian.notify.queue
RoutingKey: notify.event
DLQ:      youjian.notify.dlq.queue
Listener: concurrency=1~4/8, prefetch=10/20, retry max-attempts=3, default-requeue-rejected=false
```

## 二、心跳机制（重点）

### 2.1 心跳参数

| 参数 | 值 | 说明 |
|------|-----|------|
| 客户端发送间隔 | 30 秒 | 客户端每 30 秒发送 HEARTBEAT 帧 |
| 服务端响应间隔 | 30 秒 | 服务端收到后回 HEARTBEAT_ACK |
| 超时判定 | 3 次未收到 ACK | 即 90 秒无响应触发重连 |
| 心跳帧格式 | STOMP HEARTBEAT | 借用 STOMP 协议原生心跳 |

### 2.2 心跳失败后的指数退避重连

```text
重连退避序列：1s -> 2s -> 4s -> 8s -> 16s -> 32s -> 60s（封顶）
  第 1 次重连：等待 1s
  第 2 次重连：等待 2s
  第 3 次重连：等待 4s
  第 4 次重连：等待 8s
  第 5 次重连：等待 16s
  第 6 次重连：等待 32s
  第 7 次及以后：等待 60s
重连成功后计数器归零，下次失败重新从 1s 开始
```

### 2.3 心跳代码示例

**前端（JavaScript）：**

```javascript
// 心跳管理器
class HeartbeatManager {
  constructor(stompClient) {
    this.stompClient = stompClient;
    this.interval = 30000;       // 30 秒
    this.maxMissed = 3;          // 3 次未收到 ACK
    this.missedCount = 0;
    this.timer = null;
  }

  start() {
    this.sendHeartbeat();
    this.timer = setInterval(() => {
      if (this.missedCount >= this.maxMissed) {
        console.warn('心跳超时，触发重连');
        this.stop();
        ReconnectManager.reconnect();
        return;
      }
      this.sendHeartbeat();
    }, this.interval);
  }

  sendHeartbeat() {
    if (this.stompClient.connected) {
      this.stompClient.send('/app/heartbeat', {}, JSON.stringify({ ts: Date.now() }));
      this.missedCount++;
    }
  }

  onAck() {
    this.missedCount = 0;  // 收到 ACK 重置计数
  }

  stop() {
    if (this.timer) clearInterval(this.timer);
    this.timer = null;
  }
}
```

**服务端（Java）：**

```java
// 心跳处理器
@Controller
public class HeartbeatController {

    @MessageMapping("/heartbeat")
    @SendToUser("/queue/heartbeat.ack")
    public HeartbeatAck handleHeartbeat(Heartbeat beat, Principal principal) {
        // 更新客户端在线状态
        SessionManager.updateLastActive(principal.getName(), System.currentTimeMillis());
        return new HeartbeatAck("HEARTBEAT_ACK", System.currentTimeMillis());
    }
}

// 服务端侧心跳检测：扫描超时会话
@Scheduled(fixedRate = 30000)
public void scanTimeoutSessions() {
    long threshold = System.currentTimeMillis() - 90_000; // 90 秒
    SessionManager.findAll().forEach(session -> {
        if (session.getLastActive() < threshold) {
            log.warn("会话超时，主动关闭：{}", session.getUserId());
            SessionManager.close(session); // 触发客户端重连
        }
    });
}
```

## 三、断线重连策略（重点）

### 3.1 触发条件

| 触发条件 | 检测方式 | 处理 |
|---------|---------|------|
| 网络断开 | 浏览器 online/offline 事件 | 立即触发重连 |
| 心跳超时 | 3 次未收到 ACK | 触发重连 |
| 服务端主动关闭 | STOMP ERROR 帧 / onClose 事件 | 触发重连 |
| WebSocket 异常 | onerror 事件 | 触发重连 |
| 服务端重启 | 连接被重置 | 触发重连 |

### 3.2 重连流程

```text
重连流程：
  1. 关闭旧连接（避免连接泄漏）
  2. 停止心跳定时器
  3. UI 提示"网络异常，正在重连..."
  4. 等待退避时间（指数退避）
  5. 重新建立 STOMP 连接（携带 JWT Token）
  6. 连接成功后重新订阅所有 topic
  7. 调用 /api/notify/offline?since={lastMessageTime} 拉取离线消息
  8. 重启心跳定时器
  9. UI 提示"已恢复连接"，关闭重连弹窗
  10. 退避计数器归零
```

### 3.3 最大重连次数

- 最大重连次数：**无限**（直到用户主动登出或关闭页面）。
- 退避时间封顶 60 秒，避免无限增长。
- 每次重连在 UI 弹窗显示当前重连次数与下次重连倒计时。
- 用户可点击"立即重连"按钮跳过退避等待。

### 3.4 重连失败提示

```text
UI 提示规范：
  - 首次重连：右上角 toast "网络异常，正在重连..."
  - 第 3 次失败：中央弹窗 "网络连接失败，已重连 3 次，正在继续尝试..."
  - 第 10 次失败：弹窗增加"检查网络后点击重试"按钮
  - 重连成功：toast "已恢复连接"（绿色，3 秒后消失）
  - 禁止：重连期间静默无提示（用户不知情）
  - 禁止：重连期间允许提交订单（应引导用户等待）
```

### 3.5 重连代码示例

```javascript
class ReconnectManager {
  constructor(stompClient, heartbeatMgr) {
    this.stompClient = stompClient;
    this.heartbeatMgr = heartbeatMgr;
    this.attempt = 0;
    this.maxBackoff = 60000;  // 60 秒封顶
    this.subscriptions = [];  // 待重新订阅的 topic
  }

  async reconnect() {
    this.attempt++;
    const backoff = Math.min(1000 * Math.pow(2, this.attempt - 1), this.maxBackoff);
    this.showReconnectUI(this.attempt, backoff);

    await this.sleep(backoff);

    try {
      await this.stompClient.connect(this.buildHeaders());
      // 重新订阅
      this.subscriptions.forEach(sub => sub.resubscribe());
      // 拉取离线消息
      await this.fetchOfflineMessages();
      // 重启心跳
      this.heartbeatMgr.start();
      this.attempt = 0;
      this.hideReconnectUI();
    } catch (err) {
      console.error('重连失败', err);
      this.reconnect(); // 递归重试
    }
  }

  buildHeaders() {
    return { Authorization: 'Bearer ' + getToken() };
  }

  async fetchOfflineMessages() {
    const since = localStorage.getItem('lastMessageTime') || 0;
    const res = await fetch(`/api/notify/offline?since=${since}`);
    const messages = await res.json();
    messages.forEach(msg => this.handleOfflineMessage(msg));
  }

  sleep(ms) { return new Promise(r => setTimeout(r, ms)); }
}
```

## 四、消息重试机制（重点）

### 4.1 服务端发送失败重试

RabbitMQ listener 配置（项目现有配置）：

```yaml
spring:
  rabbitmq:
    listener:
      simple:
        concurrency: 1            # 最小消费者
        max-concurrency: 4        # 最大消费者（部分场景 8）
        prefetch: 10              # 预取（部分场景 20）
        retry:
          max-attempts: 3         # 最大重试 3 次
          initial-interval: 1000  # 初始间隔 1s
          multiplier: 2.0         # 乘数 2.0（1s/2s/4s）
          enabled: true
        default-requeue-rejected: false  # 重试耗尽不回队列，进 DLQ
```

重试行为：消息处理抛异常时，按 1s → 2s → 4s 间隔重试 3 次，3 次仍失败则进入死信队列（DLQ）。

### 4.2 客户端 ACK 机制

```text
客户端 ACK 机制：
  1. 服务端推送消息后，消息状态为"已送达未确认"
  2. 客户端收到消息后处理，处理成功回 ACK 帧
  3. 服务端收到 ACK 后更新 sys_notification.status = 'READ'
  4. 未 ACK 的消息视为未送达，服务端保留 7 天
  5. 客户端重连后拉取未 ACK 的离线消息重新推送
```

```javascript
// 客户端 ACK 示例
stompClient.subscribe('/user/queue/notify', (frame) => {
  const message = JSON.parse(frame.body);
  try {
    handleMessage(message);  // 业务处理
    // 处理成功，回 ACK
    stompClient.send('/app/notify/ack', {},
      JSON.stringify({ messageId: message.messageId }));
  } catch (err) {
    console.error('消息处理失败，不回 ACK，等待重投', err);
    // 不发送 ACK，服务端会重投
  }
});
```

### 4.3 死信队列（DLQ）配置

```text
DLQ 配置：
  - 死信交换机：youjian.notify.dlx.exchange
  - 死信队列：youjian.notify.dlq.queue
  - 绑定：notify.event.dlq
  - 触发条件：retry max-attempts=3 仍失败 + default-requeue-rejected=false
  - DLQ 消息保留：30 天
  - DLQ 消息不可被自动消费，必须人工介入
```

```java
// RabbitMQ 队列配置（声明 DLX 绑定）
@Bean
public Queue notifyQueue() {
    return QueueBuilder.durable("youjian.notify.queue")
        .withArgument("x-dead-letter-exchange", "youjian.notify.dlx.exchange")
        .withArgument("x-dead-letter-routing-key", "notify.event.dlq")
        .build();
}

@Bean
public Queue dlqQueue() {
    return QueueBuilder.durable("youjian.notify.dlq.queue").build();
}
```

### 4.4 DLQ 监控告警

```text
DLQ 监控告警：
  - 定时任务每 5 分钟扫描 youjian.notify.dlq.queue 消息数
  - 队列非空时触发企业微信群告警：
    "告警：RabbitMQ DLQ 有 {N} 条死信消息，请人工排查"
  - 告警包含：消息内容、失败原因、入队时间、关联订单
  - 人工处理 DLQ 消息后，标记处理结果（重新投递/丢弃/转人工）
  - DLQ 堆积 > 100 条时升级告警至电话通知
```

## 五、消息幂等性处理（重点）

### 5.1 服务端幂等：messageId 去重

```text
服务端幂等方案：
  - 每条消息分配全局唯一 messageId（UUID v4）
  - 发送前 Redis 缓存 messageId，TTL 1 小时
  - 消费前校验 messageId 是否已处理：
      已处理 -> 直接 ACK，跳过业务
      未处理 -> 执行业务，写入 Redis
  - 幂等校验与业务执行在同一个事务内
```

```java
// 服务端幂等校验
public void consume(NotifyMessage message) {
    String key = "idempotent:notify:" + message.getMessageId();
    // SETNX 原子操作，已存在则返回 false
    Boolean first = redis.opsForValue().setIfAbsent(key, "1", 1, TimeUnit.HOURS);
    if (Boolean.FALSE.equals(first)) {
        log.info("消息已处理，跳过：{}", message.getMessageId());
        return; // 幂等，直接返回
    }
    try {
        businessService.handle(message);
    } catch (Exception e) {
        redis.delete(key);  // 业务失败回滚幂等标记，允许重试
        throw e;
    }
}
```

### 5.2 客户端幂等：本地 messageId 集合

```text
客户端幂等方案：
  - 本地维护已处理 messageId 集合（IndexedDB 持久化）
  - 最大保留 1000 条，LRU 淘汰最旧
  - 收到消息先查集合：
      已存在 -> 丢弃，不重复处理
      不存在 -> 处理后写入集合
  - 重连后拉取离线消息同样走幂等校验
```

```javascript
class IdempotentStore {
  constructor() {
    this.db = new IndexedDBWrapper('notify_idempotent');
    this.maxSize = 1000;
  }

  async isDuplicate(messageId) {
    return await this.db.get(messageId) !== undefined;
  }

  async markProcessed(messageId) {
    await this.db.put(messageId, Date.now());
    if (await this.db.count() > this.maxSize) {
      const oldest = await this.db.getOldest();
      await this.db.delete(oldest);  // LRU 淘汰
    }
  }
}

// 消息处理前置校验
async function handleMessage(message) {
  if (await idempotentStore.isDuplicate(message.messageId)) {
    console.log('重复消息，丢弃', message.messageId);
    return;
  }
  await businessHandle(message);
  await idempotentStore.markProcessed(message.messageId);
}
```

### 5.3 数据库幂等：唯一索引

```sql
-- sys_notification 表幂等保障
CREATE TABLE sys_notification (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    message_id VARCHAR(64) NOT NULL COMMENT '消息唯一ID(UUID)',
    store_id BIGINT NOT NULL COMMENT '门店ID',
    biz_type VARCHAR(32) NOT NULL COMMENT '业务类型',
    biz_id VARCHAR(64) NOT NULL COMMENT '业务ID',
    event_type VARCHAR(32) NOT NULL COMMENT '事件类型',
    content JSON NOT NULL COMMENT '消息内容',
    status VARCHAR(16) NOT NULL DEFAULT 'UNREAD' COMMENT '状态',
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    UNIQUE KEY uk_message_id (message_id),                    -- messageId 幂等
    UNIQUE KEY uk_biz_event (biz_type, biz_id, event_type),   -- 业务幂等
    KEY idx_store_status (store_id, status)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='站内通知表';
```

`biz_type + biz_id + event_type` 联合唯一索引保证同一业务事件不会重复入库，即使消息重投也只会触发唯一约束冲突，业务层捕获冲突即视为已处理。

## 六、消息顺序保证

### 6.1 单一队列 FIFO

```text
顺序保证方案：
  - RabbitMQ 单队列 youjian.notify.queue 保证 FIFO（先进先出）
  - 同一订单的消息按发送顺序进入队列，消费端按顺序消费
  - 单消费者（concurrency=1）场景下顺序严格保证
  - 多消费者（concurrency>1）场景下，同一订单消息可能被不同消费者并行处理，需分区
```

### 6.2 多队列场景下的分区

```text
分区方案（高并发场景）：
  - 使用 orderId 作为 partition key
  - Exchange 类型改为 x-consistent-hash（一致性哈希）
  - 同一 orderId 的消息路由到同一队列，保证顺序
  - 不同 orderId 可并行处理，提升吞吐
  - 队列数 = 4（与 max-concurrency 匹配）

  路由示例：
    order_1001 的所有消息 -> queue_2（按 hash 路由）
    order_1002 的所有消息 -> queue_1
    同一订单消息严格按发送顺序处理
```

```java
// 一致性哈希交换机配置
@Bean
public CustomExchange consistentHashExchange() {
    Map<String, Object> args = new HashMap<>();
    args.put("hash-header", "x-order-id");  // 用 orderId 头做 hash
    return new CustomExchange("youjian.notify.hash.exchange",
        "x-consistent-hash", true, false, args);
}
```

### 6.3 顺序保证禁忌

- 禁止同一订单的消息并发处理（会破坏状态机顺序）。
- 禁止在多消费者场景下不分区（订单状态可能错乱）。
- 禁止业务层用多线程处理同一订单的消息（即使消费端有序）。

## 七、离线消息补偿

### 7.1 离线消息保留策略

```text
离线消息保留：
  - 服务端在 sys_notification 表保留 7 天离线消息
  - 消息状态：UNREAD（未读）/ READ（已读）
  - 超过 7 天的未读消息归档至 sys_notification_archive 表
  - 归档表保留 1 年，1 年后清理
```

### 7.2 离线消息拉取

```text
拉取流程：
  1. 客户端记录最后一条消息的接收时间 lastMessageTime（localStorage 持久化）
  2. 重连成功后调用 GET /api/notify/offline?since={lastMessageTime}
  3. 服务端查询 sys_notification WHERE store_id=? AND created_at > since AND status='UNREAD'
  4. 返回消息列表（按 created_at 升序）
  5. 客户端按顺序处理，每条走幂等校验
  6. 处理完成后更新 lastMessageTime 为最后一条消息时间
```

```java
// 服务端离线消息接口
@GetMapping("/api/notify/offline")
public List<NotifyMessage> getOffline(@RequestParam Long since,
                                       @RequestHeader("X-Store-Id") Long storeId,
                                       Principal principal) {
    return notifyRepo.findOffline(storeId, principal.getName(),
        new Date(since), PageRequest.of(0, 500)); // 单次最多 500 条
}
```

### 7.3 离线消息分页

- 单次最多返回 500 条，超出分页拉取。
- 客户端循环拉取直到返回空列表。
- 拉取间隔 1 秒，避免瞬间打爆服务端。

## 八、降级方案

### 8.1 WebSocket 不可用降级

```text
降级方案一：HTTP 长轮询
  - 触发条件：WebSocket 连续重连 5 次失败
  - 降级方式：客户端改为 HTTP 长轮询，间隔 5 秒
  - 轮询接口：GET /api/notify/poll?since={lastMessageTime}
  - 服务端长轮询：hold 住请求最多 30 秒，有消息立即返回
  - UI 提示：toast "实时推送不可用，已切换为轮询模式"
  - 恢复：每 5 分钟尝试恢复 WebSocket，成功后停止轮询
```

```javascript
// 降级轮询
class PollingFallback {
  constructor() {
    this.interval = 5000;
    this.timer = null;
  }

  start() {
    this.poll();
    this.timer = setInterval(() => this.poll(), this.interval);
  }

  async poll() {
    const since = localStorage.getItem('lastMessageTime') || 0;
    const res = await fetch(`/api/notify/poll?since=${since}`);
    const messages = await res.json();
    messages.forEach(msg => handleMessage(msg));
  }

  stop() {
    if (this.timer) clearInterval(this.timer);
  }
}
```

### 8.2 RabbitMQ 不可用降级

```text
降级方案二：同步入库 + 定时补偿
  - 触发条件：RabbitMQ 连接失败（NotifyPublisher 发送异常）
  - 降级方式：消息直接写入 sys_notification 表（status=PENDING）
  - 定时任务：每 30 秒扫描 PENDING 消息，RabbitMQ 恢复后补发
  - 兜底：即使 RabbitMQ 长时间不可用，客户端轮询仍能拉到消息
  - 告警：RabbitMQ 不可用立即企业微信告警
```

```java
// 降级入库
public void publish(NotifyMessage message) {
    try {
        rabbitTemplate.convertAndSend("youjian.notify.exchange",
            "notify.event", message);
    } catch (AmqpException e) {
        log.error("RabbitMQ 不可用，降级入库", e);
        notifyRepo.savePending(message);  // 写入 PENDING 状态
        alertService.send("RabbitMQ 不可用，消息降级入库");
    }
}

// 定时补偿
@Scheduled(fixedRate = 30000)
public void compensatePending() {
    List<NotifyMessage> pending = notifyRepo.findPending();
    pending.forEach(msg -> {
        try {
            rabbitTemplate.convertAndSend("youjian.notify.exchange", "notify.event", msg);
            notifyRepo.markSent(msg.getId());
        } catch (Exception ignored) {}
    });
}
```
