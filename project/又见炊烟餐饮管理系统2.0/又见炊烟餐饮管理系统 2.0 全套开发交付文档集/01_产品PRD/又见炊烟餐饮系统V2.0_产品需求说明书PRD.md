## 1. 文档说明

### 1.1 文档目的
本文档为"又见炊烟餐饮管理系统 2.0"的产品需求说明书（PRD），用于明确产品定位、用户角色、功能模块、业务流程、非功能性需求及设计风格规范，作为后续设计、开发、测试、验收与运营的唯一业务源头。所有功能取舍、接口契约、状态枚举、业务规则均以本文档及其子文档为准。

### 1.2 文档范围
覆盖宁国店（store_id=1）与宣城店（store_id=2）两家连锁门店的全业务链路，包括但不限于：用户与权限、菜品与菜单、点菜与退菜、订单与结账、桌台与看板、宴会预订与变更、采购与入库、库存与盘点、调拨与报损、报销与审批、财务与凭证、薪资与考勤、会员与营销、报表与运维等模块。

### 1.3 术语约定
| 术语 | 含义 |
|------|------|
| 门店 | 同一品牌下独立核算的经营单位，本系统门店隔离字段为 store_id |
| 沽清 | 菜品当日售罄，前台与 iPad 端不再展示可点 |
| 宴会 | 多桌、含固定菜单或套餐的大型聚餐，区别于零点 |
| 订金 | 宴会预订时客户预付的保证金，按比例可退 |
| 违约金 | 客户单方取消预订时按订单总额收取的赔偿金 |
| KDS | 后厨显示系统，负责工单推送与出菜进度 |
| GM | 超级总经理角色，跨门店全局权限 |
| RBAC | 基于角色的访问控制模型 |

## 2. 项目背景

### 2.1 行业背景
餐饮连锁行业正由"单店手工作坊"向"多店数字化协同"演进。门店层面面临宴会预订信息散乱、退订纠纷频发、库存损耗失控、跨店调拨无据、审批链路冗长等痛点；总部层面面临财务凭证割裂、薪资考勤手工核算、营销数据滞后、报表口径不一致等问题。又见炊烟品牌在宁国、宣城两地连锁经营，亟需一套覆盖前后台、贯通业财、支持多门店隔离的统一管理系统。

### 2.2 现状痛点
1. 预订信息以微信/电话为主，订金、违约金、桌位保留规则不统一，纠纷难举证。
2. 点菜 iPad 与后厨工单脱节，退菜、催菜、加菜无审计痕迹。
3. 库存以 Excel 记账，采购入库、盘点报损、跨店调拨无流水。
4. 报销与审批走纸质单据，节点超时无人跟进，财务对账困难。
5. 薪资由考勤、加班、奖惩多项合成，手工易错；会员与营销数据未沉淀。
6. 两店数据混杂，无法按门店独立核算经营指标。

### 2.3 项目目标
构建又见炊烟餐饮管理系统 2.0，实现"一店一账、业财一体、审批闭环、数据可溯"。系统在 2026 年 8 月完成核心模块上线，覆盖宁国、宣城两店日常运营，并预留第三店扩展能力。

## 3. 产品定位

### 3.1 产品定位陈述
又见炊烟餐饮管理系统 2.0 是一套面向徽派雅致餐饮连锁门店的中后台一体化 SaaS 系统，以"多门店隔离 + 业财一体 + 审批闭环"为核心差异点，服务从预订、点菜、出菜、结账到采购、库存、报销、薪资、营销的全链路。

### 3.2 价值主张
- 对老板：跨店经营数据一目了然，财务凭证自动生成，决策有据。
- 对店长：本店预订、桌台、出菜、库存全流程可视，异常自动告警。
- 对服务员：iPad 点菜与桌台看板联动，退菜催菜有据可查。
- 对厨师长：后厨工单实时推送，沽清与出菜进度同步。
- 对财务/采购/库管：单据流转与审批闭环，账实相符。

### 3.3 目标用户与场景
主要服务于中高端徽派餐饮连锁门店的日常运营管理，覆盖堂食、宴会、套餐、零点等多种业态，兼顾前厅服务、后厨生产、后台管理与移动审批。

## 4. 用户角色

系统采用 RBAC 五表模型（sys_role / sys_permission / sys_menu / sys_user_role / sys_role_permission），预设 8 类业务角色，叠加 1 个超级总经理角色。各角色数据范围由 data_scope 控制（all=跨门店、store=本门店）。

| 角色 | 角色编码 | data_scope | 职责描述 |
|------|----------|------------|----------|
| 超级总经理 | GM | all | 跨门店全局管理，全部权限，财务/薪资/采购/权限/审计 |
| 老板（总部） | HQ_OWNER | all | 经营决策、报表查看、跨店对比、营销与会员策略制定 |
| 店长 | STORE_MANAGER | store | 本店经营管理、人员排班、预订审批、库存与采购初审 |
| 服务员 | WAITER | store | iPad 点菜、桌台看板、退菜催菜、客户接待 |
| 厨师长 | CHEF | store | 后厨工单处理、沽清设置、出菜进度、菜品配方维护 |
| 收银员 | CASHIER | store | 结账、退款、开票、收银对账、订金收取 |
| 财务 | FINANCE | store/all | 凭证录入、报销支付、应收应付、对账、报表 |
| 采购 | PURCHASER | store | 采购申请、供应商对账、入库、价格维护 |
| 库管 | KEEPER | store | 入库出库、盘点、报损、调拨、库存预警 |

## 6. 核心业务流程

### 6.1 宴会预订端到端流程
1. 客户致电/到店，服务员在预订管理创建预订（预订类型=宴会，选场合、桌数、人数、套餐/模板）。
2. 系统按订金规则计算订金（默认 30%，最低 500 元），收银员收取订金，预订状态由"待确认"流转为"已确认"，桌位被占用。
3. 客户可变更预订（换桌、改人数、改菜品），系统记录变更日志；可取消预订，按退款比例（开餐前 ≥24h 退 100%、24~6h 退 50%、<6h 不退）与违约金规则结算。
4. 开餐前由服务员/店长复核桌位与菜单，发送后厨工单。
5. 用餐结束，收银员结账（合并订金抵扣、折扣、优惠券、会员卡），生成结账单，桌位释放。
6. 财务凭证自动生成，会员积分入账，营销数据回流。

### 6.2 点菜与后厨联动流程
1. 服务员在 iPad 端选择桌台，进入点菜界面，浏览分类与套餐。
2. 加菜时校验沽清状态，下单后通过 RabbitMQ 推送后厨工单（KDS）。
3. 后厨接单→烹饪中→已出菜，状态回写 iPad；催菜触发加急标记。
4. 退菜需选择退菜原因，记录退菜流水，同步扣减后厨工单与菜品销量。
5. 结账时按实际消费明细结算，沽清与退菜不影响已上桌菜品。

### 6.3 采购入库与库存联动流程
1. 库管/厨师长发起采购申请（关联原料、数量、建议供应商）。
2. 采购员确认生成采购单，发往供应商；到货后录入入库单（采购收货）。
3. 入库单审核通过后，库存汇总表（inventory_summary）增加，原料库存日志（ingredient_inventory_log）写入流水。
4. 库存低于安全库存阈值（默认 20%）触发预警，推送库管与采购。
5. 盘点周期（默认 30 天）生成盘点任务，盘盈盘亏生成报损单，财务记账。

### 6.4 报销审批流程
1. 员工提交报销单（关联费用类型、金额、附件）。
2. 按审批模板流转：店长初审→财务复核→GM 终审（超阈值）。
3. 审批超时（默认 48 小时）自动升级上一级。
4. 终审通过后财务出款，报销状态置"已支付"，凭证生成。

### 6.5 薪资结算流程
1. 月末排班与考勤数据归集，系统按薪资模板计算基础工资。
2. 叠加加班、奖惩、社保扣款，生成月度薪资单（month_salary）。
3. 店长/GM 复核确认，财务发放，凭证生成。

## 7. 非功能性需求

### 7.1 性能需求
| 指标 | 目标值 |
|------|--------|
| 列表接口响应（P95） | ≤ 500ms |
| 详情接口响应（P95） | ≤ 300ms |
| iPad 点菜下单端到端 | ≤ 1.5s（含后厨推送） |
| 并发在线用户 | ≥ 200（两店合计） |
| 报表查询（月度） | ≤ 3s |
| 数据库单表行数上限 | 1000 万行（超出按年归档） |

### 7.2 安全需求
- 鉴权：JWT Token，有效期可配置；敏感操作二次校验。
- 传输：全站 HTTPS，生产环境 HSTS 开启。
- 加密：银行账号、身份证号采用 AES-256-GCM 加密存储，前端脱敏显示。
- 限流：RateLimitInterceptor 按 IP/用户限流，防止接口滥用。
- 审计：所有写操作经 AuditLogAspect 留痕，操作日志保留 ≥ 1 年。
- 越权防护：StoreDataScopeAspect 自动注入 store_id 过滤，店长不可伪造 storeId。

### 7.3 可用性需求
| 指标 | 目标值 |
|------|--------|
| 系统可用性 | ≥ 99.5%（年宕机 ≤ 44 小时） |
| 故障恢复（RTO） | ≤ 2 小时 |
| 数据恢复（RPO） | ≤ 15 分钟（MySQL 主从 + 定时备份） |
| 备份策略 | 每日全量 + 实时 binlog，备份上传腾讯云 COS |
| 容错 | 单点失败不影响其他模块，RabbitMQ 消息持久化 |

### 7.4 可维护性与扩展性
- 后端分层：Controller / Service / Repository / Entity / DTO，职责清晰。
- 多门店扩展：新增门店仅需插入 store_info 与配置项，无需改代码。
- 字典与配置驱动：状态枚举、业务规则均入库管理，避免硬编码。
- 迁移脚本版本化：scripts/migrations 下按 v1/v2 版本递进，可回溯。

## 8. 多门店隔离

### 8.1 隔离模型
所有业务表强制包含 `store_id BIGINT NOT NULL` 字段，约定 0=全局、1=宁国店、2=宣城店。共享数据（字典、配置默认值、角色、权限）store_id=0。

### 8.2 隔离实现
- 查询过滤：所有 SELECT 经 StoreDataScopeAspect 切面自动追加 `WHERE store_id=?`，按当前用户 UserContext.getCurrentStoreId() 注入。
- 写入隔离：店长（非 GM）写入强制使用当前门店 store_id，防止伪造。
- 跨店访问：仅 GM 角色 data_scope=all 可跨门店查询与写入。
- 分门店配置：业务规则配置采用 `<rule>__s<store_id>` 命名约定，支持分门店差异化（如宣城店违约金比例可独立设置）。

### 8.3 隔离验证
上线前需验证：宁国店账号不可查询/修改宣城店预订、库存、财务数据；GM 账号可跨店汇总但不可越权改单店数据；报表按门店维度聚合，跨店合计需显式授权。

## 9. 徽派雅致设计风格说明

### 9.1 设计理念
系统视觉取意徽派建筑的粉墙黛瓦、马头墙线条与水墨留白，传达雅致、内敛、稳重的品牌气质，区别于市面大红大紫的餐饮系统。整体配色低饱和度，强调留白与对称。

### 9.2 配色规范
| 用途 | 色值 | 说明 |
|------|------|------|
| 主背景 | #F5F3EE 米白 | 模拟粉墙底色 |
| 主文字 | #2C2C2C 墨黑 | 黛瓦色 |
| 辅助文字 | #6B6B6B 灰墨 | 次级信息 |
| 主强调 | #8B7355 赭石 | 徽派木构色，用于选中/标题 |
| 选中高亮 | #C9A86A 古金 | 选中元素金边高亮 |
| 成功 | #6B8E6B 竹青 | 成功状态 |
| 警告 | #C9A86A 古金 | 警告状态 |
| 危险 | #A0524D 朱赭 | 退菜/报错，非大红 |
| 分隔线 | #E3E0D8 浅米 | 卡片分隔 |

### 9.3 布局与交互规范
- 布局：宽页面横向排列，多行对称；弹窗宽度 50vw。
- 圆角：不使用圆角或仅使用 16px 圆角。
- 输入框：高度 32px，窄宽度。
- 数字控件：减号(-)在左，加号(+)在右。
- 时间显示：创建时间单行显示。
- 图标：禁用 Emoji/SVG 图标，使用纯文字标签。
- 选中态：选中元素金边高亮，非填充色块。
- 响应式：移动端友好，使用原生选择器与底部抽屉。

### 9.4 字体规范
正文使用系统默认无衬线字体（PingFang SC / Microsoft YaHei），标题加粗；数字与金额使用等宽字体对齐，便于扫读。
