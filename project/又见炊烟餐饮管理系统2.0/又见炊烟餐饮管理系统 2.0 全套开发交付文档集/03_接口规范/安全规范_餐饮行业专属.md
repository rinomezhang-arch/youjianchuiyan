## 文档目的

本规范在通用 Web 安全基础上，针对餐饮行业特有场景（客户手机号、会员隐私、收银支付、押金退款）制定强制安全要求。餐饮业务涉及大量个人敏感信息与资金流转，一旦泄露或被篡改将造成严重法律与商誉风险。本规范所有条款为强制项，CI 流水线与代码评审必须逐项核对，违反任意条款的 PR 不得合并。

## 一、总则与安全原则

### 1.1 五大安全原则

| 原则 | 含义 | 落地措施 |
|------|------|---------|
| 最小权限 | 角色仅授予完成业务所需的最小权限 | RBAC 细粒度授权 + 数据行级过滤 |
| 职责分离 | 敏感操作发起与审批不得同一人 | 三级审批流 + 双因子校验 |
| 可审计 | 所有敏感操作必须留痕且不可篡改 | audit_log 表 + 写入即不可改 |
| 可追溯 | 任意数据变更可定位到人与时间 | operator_id + operate_time + IP + 设备指纹 |
| 纵深防御 | 多层防护叠加，单层失效不致全盘失守 | 网关 + 应用 + 数据库 + 日志 四层 |

### 1.2 法规对标

- 《中华人民共和国个人信息保护法》（PIPL）
- 《中华人民共和国数据安全法》
- 《个人信息安全规范》（GB/T 35273-2020）
- 《支付卡行业数据安全标准》（PCI DSS）适用于银行卡支付场景
- GDPR（面向外籍会员客户场景对齐）

### 1.3 敏感数据分级

| 级别 | 定义 | 示例 | 存储要求 | 传输要求 |
|------|------|------|---------|---------|
| L1 极敏感 | 直接身份识别 + 资产 | 身份证号、银行卡号 | AES-256 加密 + 字段级密钥 | TLS 1.3 + 二次授权 |
| L2 敏感 | 个人隐私 + 联系方式 | 手机号、地址、生日 | 脱敏存储 + 明文仅授权可见 | TLS 1.3 |
| L3 内部 | 业务数据 | 订单、积分、余额 | 明文 + 行级权限 | TLS 1.2+ |
| L4 公开 | 公共信息 | 菜品、门店信息 | 明文 | HTTPS |

## 二、客户手机号脱敏规范（重点）

### 2.1 脱敏展示规则

| 场景 | 展示形式 | 权限要求 |
|------|---------|---------|
| 列表展示（订单/会员列表） | 138****8888（隐藏中间 4 位） | 任意登录用户 |
| 详情查看（会员详情） | 13888888888（明文） | 店长及以上角色 + 短信验证码二次授权 |
| 短信通知发送 | 明文（仅发送通道） | 系统内部，不展示给用户 |
| 导出 Excel/CSV | 禁止导出原始手机号 | 任何角色均禁止 |
| 日志记录 | 138****8888 | 任何日志均脱敏 |
| 异常堆栈 | 138****8888 | 全局异常切面统一脱敏 |

### 2.2 代码层面实现：@Desensitize 注解 + Jackson 序列化器

```java
// 注解定义
@Target({ElementType.FIELD})
@Retention(RetentionPolicy.RUNTIME)
@JacksonAnnotationsInside
@JsonSerialize(using = DesensitizeSerializer.class)
public @interface Desensitize {
    DesensitizeType value() default DesensitizeType.MOBILE;
}

// 枚举类型
public enum DesensitizeType {
    MOBILE,       // 138****8888
    ID_CARD,      // 340***********1234
    BANK_CARD,    // 6222**********1234
    ADDRESS,      // 安徽省宁国市****
    NAME,         // 张*
    EMAIL         // z***@example.com
}

// 使用示例（不修改业务实体，仅声明注解）
public class MemberVO {
    @Desensitize(DesensitizeType.MOBILE)
    private String mobile;

    @Desensitize(DesensitizeType.NAME)
    private String realName;
}
```

```java
// 序列化器核心逻辑
public class DesensitizeSerializer extends JsonSerializer<String>
        implements ContextualSerializer {
    private DesensitizeType type;

    @Override
    public void serialize(String value, JsonGenerator gen, SerializerProvider sp)
            throws IOException {
        // 明文查看需通过 SecurityContext 校验二次授权
        if (type == DesensitizeType.MOBILE
                && AuthContext.hasPlainTextPermission()) {
            gen.writeString(value); // 已二次授权，返回明文
        } else {
            gen.writeString(DesensitizeUtil.mask(value, type));
        }
    }
}
```

### 2.3 二次授权流程

```text
店长查看会员明文手机号流程：
  1. 前端点击"查看完整手机号"按钮
  2. 后端校验角色 >= 店长（store_manager / boss / owner）
  3. 后端向会员预留手机号发送 6 位短信验证码（5 分钟有效）
  4. 店长输入验证码，后端校验通过后下发 5 分钟有效的 plaintext_token
  5. 后续请求携带 plaintext_token，序列化器返回明文
  6. 全过程写入 audit_log：操作人、IP、设备指纹、目标会员、时间
```

### 2.4 导出限制

- 禁止任何角色通过 Excel/CSV 导出原始手机号字段。
- 导出接口必须强制脱敏，导出列固定为 `138****8888` 形式。
- 导出操作必须记录至 audit_log，包含导出人、导出行数、导出时间。
- CI 扫描导出相关代码，禁止出现 `mobile` 字段直接写入 POI Cell。

## 三、会员隐私信息保护（重点）

### 3.1 会员信息分级存储

| 字段 | 级别 | 存储方式 | 访问控制 |
|------|------|---------|---------|
| id_card 身份证号 | L1 | AES-256 加密 | 仅老板 + 财务，二次授权 |
| bank_account 银行账号 | L1 | AES-256 加密 | 仅财务，二次授权 |
| address 地址 | L1 | AES-256 加密 | 店长及以上 |
| emergency_contact 紧急联系人 | L1 | AES-256 加密 | 店长及以上 |
| birthday 生日 | L2 | 明文 + 行级权限 | 店员及以上 |
| mobile 手机号 | L2 | 脱敏展示 + 明文加密存储 | 见第二章 |
| real_name 真实姓名 | L2 | 脱敏展示 | 任意登录用户 |
| member_level 等级 | L3 | 明文 | 任意登录用户 |
| points 积分 | L3 | 明文 + 变更留痕 | 系统内部 |
| balance 余额 | L3 | 明文 + 变更留痕 | 系统内部 |

### 3.2 AES-256 加密字段清单与实现

```java
// 加密字段清单（强制）
AES_ENCRYPT_FIELDS = [
    "member.id_card",
    "member.bank_account",
    "member.address",
    "member.emergency_contact",
    "vip_customer.id_card",
    "vip_customer.bank_account"
]

// 加密规范
- 算法：AES-256-GCM（带认证标签，防篡改）
- 密钥：字段级独立密钥，存于 KMS / Vault，禁止硬编码
- IV：每次加密随机生成 12 字节，与密文一同存储
- 密钥轮换：每 90 天轮换一次，旧密文按计划重新加密
- 禁止：ECB 模式、固定 IV、密钥写入配置文件或环境变量明文
```

```java
// 实体字段加密示例（使用 AttributeConverter）
@Convert(converter = AesEncryptConverter.class)
@Column(name = "id_card")
private String idCard;

// Converter 核心逻辑
public class AesEncryptConverter implements AttributeConverter<String, String> {
    @Override
    public String convertToDatabaseColumn(String value) {
        return value == null ? null : AesUtil.encrypt(value, KeyManager.get("id_card"));
    }
    @Override
    public String convertToEntityAttribute(String dbValue) {
        return dbValue == null ? null : AesUtil.decrypt(dbValue, KeyManager.get("id_card"));
    }
}
```

### 3.3 积分/余额变更双因子校验

会员积分与余额涉及资产，任何变更必须双因子校验。

```text
双因子校验流程：
  1. 操作员发起积分/余额变更（如手动调整、退款回滚）
  2. 系统校验操作员角色权限（店长及以上）
  3. 系统向操作员手机发送 6 位验证码（5 分钟有效）
  4. 操作员输入验证码 + 操作原因（必填，不少于 10 字）
  5. 系统校验验证码通过后执行变更
  6. 变更前后值、差额、操作人、原因、时间写入 member_balance_log
  7. 同步推送站内通知至会员本人
```

### 3.4 会员注销：30 天冷静期 + 数据匿名化

```text
会员注销流程（GDPR 对齐）：
  1. 会员发起注销申请
  2. 系统校验无未结订单、无未退押金、余额已清零
  3. 进入 30 天冷静期，期间会员可登录撤销注销
  4. 冷静期内停止一切营销推送，保留交易数据
  5. 30 天后执行数据匿名化：
     - mobile → 随机脱敏值（如 138****0000）
     - real_name → "已注销会员"
     - id_card / bank_account / address / emergency_contact → 置 NULL
     - 保留订单、积分日志用于财务对账（合法利益基础）
  6. 匿名化操作写入 audit_log，不可逆
  7. 注销完成通知会员本人
```

## 四、收银支付接口防重放（重点）

### 4.1 请求幂等键

| 要素 | 规范 |
|------|------|
| Header 名 | X-Idempotency-Key |
| 值格式 | UUID v4 |
| 存储位置 | Redis，key = `idem:pay:{storeId}:{orderId}:{key}` |
| 有效期 | 30 分钟 |
| 命中处理 | 返回首次请求的完整响应，不重复执行业务逻辑 |

```java
// 幂等拦截器核心逻辑
@Component
public class IdempotencyInterceptor implements HandlerInterceptor {
    @Override
    public boolean preHandle(HttpServletRequest req, HttpServletResponse resp,
                             Object handler) throws Exception {
        String key = req.getHeader("X-Idempotency-Key");
        if (key == null || !isValidUuid(key)) {
            resp.sendError(400, "缺少 X-Idempotency-Key 或格式错误");
            return false;
        }
        String redisKey = "idem:pay:" + StoreContext.getStoreId() + ":"
                + OrderContext.getOrderId() + ":" + key;
        String cached = redis.get(redisKey);
        if (cached != null) {
            resp.getWriter().write(cached); // 返回首次响应
            return false;
        }
        IdempotencyContext.set(redisKey); // 业务执行后写入
        return true;
    }
}
```

### 4.2 签名机制

```text
签名规范：
- 算法：HMAC-SHA256
- 密钥：每个门店独立密钥，存于 KMS，禁止硬编码
- 签名内容：method + path + body + timestamp + nonce
- 时间戳：Unix 毫秒，允许偏差 ±5 分钟
- nonce：随机字符串，Redis 缓存 10 分钟防重放
- 传输：Header X-Signature 与 X-Timestamp 与 X-Nonce

校验顺序：
  1. 时间戳偏差 > 5 分钟 → 拒绝（401）
  2. nonce 已存在于 Redis → 拒绝（401，疑似重放）
  3. 签名不匹配 → 拒绝（401）
  4. 校验通过，nonce 写入 Redis（10 分钟）
```

```java
// 签名校验示例
public class SignatureVerifier {
    public boolean verify(PayRequest req) {
        long now = System.currentTimeMillis();
        if (Math.abs(now - req.getTimestamp()) > 5 * 60 * 1000L) {
            throw new BizException(401, "时间戳超出 ±5 分钟窗口");
        }
        if (redis.hasKey("nonce:" + req.getNonce())) {
            throw new BizException(401, "nonce 已使用，疑似重放");
        }
        String data = req.getMethod() + req.getPath() + req.getBody()
                + req.getTimestamp() + req.getNonce();
        String expected = HmacUtils.hmacSha256Hex(storeSecret, data);
        if (!expected.equals(req.getSignature())) {
            throw new BizException(401, "签名校验失败");
        }
        redis.set("nonce:" + req.getNonce(), "1", 10, TimeUnit.MINUTES);
        return true;
    }
}
```

### 4.3 二维码防截屏

- 收银二维码页面（Vue 组件）启用前端防截屏：调用 `navigator.mediaDevices.getDisplayMedia` 监控 + CSS 水印（操作员姓名 + 时间 + 门店）。
- 移动端 H5 调用 `window.navigator.userAgent` 检测截屏事件，触发后立刻刷新二维码。
- 二维码有效期 60 秒，过期自动刷新。
- 二维码内容不含明文金额，仅含 orderId，金额由服务端二次校验。

### 4.4 支付通道回调验签

- 微信/支付宝回调必须验签，验签失败一律拒绝并告警。
- 回调响应必须返回 SUCCESS，但业务幂等处理（同一笔回调多次到达只处理一次）。
- 回调金额必须与订单金额一致，不一致告警并人工介入。
- 回调 IP 白名单：仅放行支付平台官方 IP 段。

### 4.5 同一订单重复支付限制

```text
规则：
- 同一订单 5 分钟内不允许重复发起支付请求（Redis 锁 pay:lock:{orderId}，TTL 5 分钟）
- 订单状态为"已支付"时，再次发起支付直接拒绝
- 订单超时未支付（30 分钟）自动关闭，关闭后不可支付
- 支付失败后允许重试，但需间隔 5 分钟且重新生成支付单号
```

## 五、押金退款接口权限校验（重点）

### 5.1 三级审批流

| 退款金额 | 审批层级 | 审批人角色 | SLA |
|---------|---------|-----------|-----|
| ≤ 500 元 | 一级 | 店长（store_manager） | 2 小时 |
| 500 - 5000 元 | 二级 | 财务（finance） | 4 小时 |
| ≥ 5000 元 | 三级 | 老板（boss / owner） | 8 小时 |

```text
审批流逻辑：
  1. 发起人提交退款申请（任何有权限角色）
  2. 系统根据金额自动路由到对应审批层级
  3. 审批人通过或拒绝，拒绝需填写原因
  4. 通过后进入下一层级（如金额 ≥5000 需店长→财务→老板三级全通过）
  5. 最终通过后执行退款，调用支付通道退款接口
  6. 退款结果回调更新订单状态，写入 refund_log
```

### 5.2 退款前置校验

```java
// 退款接口必须校验
public class RefundValidator {
    public void validate(RefundRequest req) {
        // 1. 原订单存在且未退款
        Order order = orderRepo.findById(req.getOrderId())
                .orElseThrow(() -> new BizException("原订单不存在"));
        if (order.getRefundStatus() == RefundStatus.REFUNDED) {
            throw new BizException("订单已退款，禁止重复退款");
        }
        // 2. 退款金额不超过原订单实际支付金额
        if (req.getAmount().compareTo(order.getActualPayAmount()) > 0) {
            throw new BizException("退款金额超过实付金额");
        }
        // 3. 订单归属当前门店（多租户隔离）
        if (!order.getStoreId().equals(StoreContext.getStoreId())) {
            throw new BizException("越权访问其他门店订单");
        }
        // 4. 操作人权限校验
        if (!AuthContext.hasRefundPermission(req.getAmount())) {
            throw new BizException("无权限发起此金额退款");
        }
    }
}
```

### 5.3 操作留痕

退款操作必须记录以下信息至 audit_log：

| 字段 | 说明 |
|------|------|
| operator_id | 操作人 ID |
| operator_name | 操作人姓名 |
| operate_time | 操作时间（毫秒） |
| ip | 操作人 IP（含 X-Forwarded-For 链） |
| device_fingerprint | 设备指纹（浏览器指纹 + UA） |
| geo_location | 地理位置（IP 反查城市级，不涉及精确定位） |
| order_id | 关联订单 |
| refund_amount | 退款金额 |
| reason | 退款原因 |

### 5.4 并发退款防护

```text
双重锁机制：
  1. Redis 分布式锁：refund:lock:{orderId}，TTL 30 秒，获取失败直接拒绝
  2. 数据库行锁：SELECT ... FROM order WHERE id = ? FOR UPDATE
  3. 状态机校验：退款前再次确认订单状态为"待退款"而非"已退款"
  4. 乐观锁兜底：order 表 version 字段，更新失败回滚事务

禁止：
  - 仅用 Redis 锁不加数据库锁（Redis 故障时可能并发）
  - 仅用数据库锁不加状态校验（锁内仍需校验状态）
```

## 六、通用安全防护

### 6.1 XSS 防护

- 输入过滤：所有用户输入经 `XssFilter` 过滤 `<script>`、`onerror=` 等危险标签。
- 输出编码：Vue 模板默认转义（`{{ }}`），禁止使用 `v-html` 渲染用户输入。
- 富文本场景使用 DOMPurify 白名单过滤。
- Cookie 设置 `HttpOnly` + `SameSite=Strict`。

### 6.2 SQL 注入防护

- 强制使用 JPA / MyBatis 参数化查询，禁止字符串拼接 SQL。
- 动态排序字段必须白名单校验（防止 `ORDER BY ${param}` 注入）。
- CI 扫描 `@Query` 注解中的字符串拼接，发现即拦截。
- 数据库账号最小权限：业务账号禁止 DDL 权限，DDL 走独立账号。

```java
// 禁止
@Query("SELECT o FROM Order o WHERE o.name = '" + name + "'")

// 正确
@Query("SELECT o FROM Order o WHERE o.name = :name")
List<Order> findByName(@Param("name") String name);
```

### 6.3 CSRF 防护

- SameSite Cookie：所有业务 Cookie 设置 `SameSite=Lax`。
- Token 模式：前后端分离架构使用 Bearer Token，不依赖 Cookie 鉴权。
- 敏感操作（支付、退款）强制二次确认 + CSRF Token。

### 6.4 越权防护

| 类型 | 场景 | 防护措施 |
|------|------|---------|
| 水平越权 | A 店员工访问 B 店订单 | 所有查询强制带 store_id 条件 |
| 垂直越权 | 普通店员调用店长接口 | RBAC 权限注解 + 网关鉴权 |
| 数据越权 | 通过遍历 ID 访问他人订单 | 资源所有权校验（owner_id == current_user） |
| 接口越权 | 未授权访问内部接口 | 网关白名单 + 内网隔离 |

### 6.5 文件上传安全

- 白名单：仅允许 jpg/png/pdf/xlsx，MIME 与扩展名双重校验。
- 病毒扫描：上传后调用 ClamAV 扫描，阳性直接删除。
- 大小限制：单文件 ≤ 10MB，单次请求 ≤ 30MB。
- 存储隔离：上传文件存独立 OSS Bucket，禁止与代码同库。
- 文件名重写：服务端生成 UUID 文件名，禁止保留原文件名。
- 图片处理：服务端强制重新编码（防图片马）。

## 七、审计日志规范

### 7.1 必须留痕的敏感操作

| 类别 | 操作 | 日志内容 |
|------|------|---------|
| 手机号 | 查看明文手机号 | 操作人、目标会员、授权方式 |
| 会员 | 注销、积分调整、余额调整 | 操作人、变更前后值、原因 |
| 支付 | 发起支付、支付回调 | 订单、金额、通道、结果 |
| 退款 | 发起退款、审批、执行 | 操作人、金额、审批链、结果 |
| 退款 | 退款失败、退款回滚 | 失败原因、影响范围 |
| 权限 | 角色变更、权限分配 | 操作人、目标用户、变更内容 |
| 登录 | 登录成功/失败、登出 | 账号、IP、设备指纹、结果 |
| 数据 | 导出 Excel/CSV | 操作人、行数、字段清单 |

### 7.2 审计日志存储要求

- audit_log 表只增不改不删，禁止任何 UPDATE/DELETE。
- 日志保留期 ≥ 3 年（餐饮行业财务合规要求）。
- 日志同步至独立日志库（Elasticsearch），防主库被篡改。
- 日志字段加密存储敏感值（如手机号脱敏）。
- 日志查询需独立权限，仅老板 + 审计角色可查。

### 7.3 审计日志结构

```sql
CREATE TABLE audit_log (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    store_id BIGINT NOT NULL COMMENT '门店ID',
    operator_id BIGINT NOT NULL COMMENT '操作人ID',
    operator_name VARCHAR(64) NOT NULL COMMENT '操作人姓名',
    operate_time DATETIME(3) NOT NULL COMMENT '操作时间',
    ip VARCHAR(64) NOT NULL COMMENT '操作IP',
    device_fingerprint VARCHAR(128) COMMENT '设备指纹',
    biz_type VARCHAR(32) NOT NULL COMMENT '业务类型',
    biz_id VARCHAR(64) NOT NULL COMMENT '业务ID',
    action VARCHAR(32) NOT NULL COMMENT '动作',
    detail JSON COMMENT '详情',
    result VARCHAR(16) NOT NULL COMMENT '结果 success/fail',
    INDEX idx_store_time(store_id, operate_time),
    INDEX idx_biz(biz_type, biz_id)
) COMMENT '审计日志表';
```

## 八、安全漏洞响应流程

### 8.1 响应流程

| 阶段 | 操作 | 时效 | 责任人 |
|------|------|------|--------|
| 发现 | 内部发现或外部报告，记录至漏洞台账 | 立即 | 安全负责人 |
| 评估 | 定级（P0/P1/P2/P3），评估影响范围 | 2 小时 | 安全负责人 + 架构师 |
| 修复 | 在 hotfix-* 分支修复，PR 加急审核 | P0 4h / P1 24h / P2 72h | 开发负责人 |
| 测试 | 回归 + 专项安全测试 | 修复后立即 | 测试负责人 |
| 发布 | 紧急发布，打 hotfix 标签 | 测试通过后 | 运维 |
| 通报 | 通知受影响门店与客户（如涉及数据泄露） | 24 小时 | 公关 + 老板 |
| 复盘 | 提交事故复盘报告，沉淀改进措施 | 5 个工作日 | 全员 |

### 8.2 漏洞定级标准

| 级别 | 定义 | 示例 | 响应时效 |
|------|------|------|---------|
| P0 | 资金损失或大规模数据泄露 | 支付接口可被重放、手机号可被批量导出 | 4 小时修复 |
| P1 | 单店数据泄露或核心功能瘫痪 | 越权访问其他门店订单 | 24 小时修复 |
| P2 | 非核心功能漏洞 | XSS 反射型漏洞 | 72 小时修复 |
| P3 | 安全增强建议 | Cookie 缺少 Secure 标志 | 下一版本修复 |

### 8.3 禁止行为

- 禁止私下修复漏洞不上报（必须走漏洞台账）。
- 禁止在公开仓库 Issue 描述漏洞细节（使用私有渠道报告）。
- 禁止修复后不更新安全规范（应沉淀为新的检查项）。
- 禁止 AI 角色独立处理 P0/P1 漏洞（必须人工主导）。
