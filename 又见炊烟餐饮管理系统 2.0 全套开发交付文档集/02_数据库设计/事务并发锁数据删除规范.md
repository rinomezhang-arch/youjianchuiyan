# 事务 / 并发锁 / 数据删除规范

> 适用：所有后端 Controller / Service 层  
> 维护：地龙（DL-BOT）  
> 更新：2026-08-02

---

## 1. 事务边界

### 1.1 强制事务
- **写操作**（POST/PUT/DELETE）一律加 `@Transactional`
- **跨表写**（如预订+桌台、点单+库存、报销+账务）必须事务保证原子性

### 1.2 事务传播
| 场景 | 传播行为 | 说明 |
|------|---------|------|
| 单表 CRUD | `REQUIRED`（默认） | 当前有事务加入，无则新建 |
| 嵌套调用 | `REQUIRES_NEW` | 独立事务（如审计日志，主事务回滚不影响日志记录） |
| 只读查询 | `@Transactional(readOnly=true)` | 优化查询性能 |
| 批量操作 | `REQUIRED` | 失败整批回滚 |

### 1.3 异常回滚

```java
@Transactional
public Result<?> doSave(...) {
    try {
        // 业务逻辑
        return Result.success(...);
    } catch (Exception e) {
        // 显式标记回滚（避免 try-catch 吞没异常导致事务不回滚）
        TransactionAspectSupport.currentTransactionStatus().setRollbackOnly();
        return Result.error(500, "操作失败: " + e.getMessage());
    }
}
```

**关键**：`@Transactional` 默认仅对 `RuntimeException` 和 `Error` 回滚；如需 `Checked Exception` 也回滚，需显式配置 `rollbackFor = Exception.class`。

## 2. 并发锁

### 2.1 乐观锁
适用：高频读、低冲突场景（如菜品查看、桌台查询）

```java
@Column(name = "version")
@Version
private Integer version;
// JPA 自动在 UPDATE 时 WHERE version=? AND ...，冲突时抛 OptimisticLockException
```

### 2.2 悲观锁
适用：高冲突资源（如预订同一桌台、库存扣减）

```java
// 方式1：JPA EntityManager 锁定
Order order = em.find(Order.class, id, LockModeType.PESSIMISTIC_WRITE);

// 方式2：JdbcTemplate SELECT ... FOR UPDATE
String sql = "SELECT * FROM table_master WHERE table_id=? AND store_id=? FOR UPDATE";
```

### 2.3 桌台占用关键场景
预订创建时占用桌台，必须串行化：
```sql
-- 步骤1：检查桌台是否被占用（行锁）
SELECT * FROM table_master WHERE table_id=? AND store_id=? FOR UPDATE;
-- 步骤2：判断状态
-- 步骤3：占用
UPDATE table_master SET table_status='reserved' WHERE table_id=?;
-- 步骤4：插入预订-桌台关联
INSERT INTO booking_table (booking_id, table_id, ...) VALUES (...);
```

### 2.4 唯一约束兜底
即使有应用层锁，数据库层仍必须有 `UNIQUE` 约束兜底：
- `uk_booking_id`（订单号唯一）
- `uk_store_name_phone`（同店同客户唯一）
- `uk_role_perm`（角色-权限关联唯一）

## 3. 数据删除规范

### 3.1 禁止物理删除
**所有业务表禁止 `DELETE FROM ...`**，统一使用逻辑删除：

```sql
-- ❌ 错误：物理删除
DELETE FROM customer_master WHERE customer_id=1;

-- ✅ 正确：逻辑删除（更新 is_active 字段）
UPDATE customer_master SET is_active=0, updated_at=NOW() WHERE customer_id=1;
```

### 3.2 逻辑删除字段
| 字段名 | 类型 | 说明 |
|--------|------|------|
| `is_active` | `TINYINT` | 1=启用 0=停用（推荐，已有表多用此） |
| `is_deleted` | `TINYINT` | 0=未删 1=已删（新表可选） |

> **现状**：项目已统一使用 `is_active`，新表请保持一致。

### 3.3 查询过滤
所有查询必须显式过滤已停用记录：
```sql
SELECT * FROM customer_master WHERE store_id=? AND is_active=1;
```

### 3.4 关联数据保护
删除主记录前，必须先处理子记录：
```java
// 示例：删除套餐前，先停用其菜品明细
@Transactional
public Result<?> deletePackage(Long packageId) {
    packageRepo.deactivate(packageId);  // 主表 is_active=0
    packageDishRepo.deactivateByPackageId(packageId);  // 子表 is_active=0
    return Result.success();
}
```

### 3.5 审计日志
所有删除/停用操作必须留痕到 `audit_log` / `change_log`：
```java
auditLogRepo.save(new AuditLog()
    .setAction("DELETE")
    .setEntityType("customer")
    .setEntityId(customerId)
    .setBeforeData(jsonBefore)  // 删除前快照
    .setOperatorId(UserContext.getCurrentUserId())
    .setOperatorName(UserContext.getCurrentUserName())
);
```

## 4. 幂等性

### 4.1 创建接口
对唯一约束冲突采用 upsert 语义，避免 `DuplicateKeyException`：
```java
// 客户创建：若同店同手机号已存在，返回已有记录
List<Map<String, Object>> existing = jdbc.queryForList(
    "SELECT customer_id FROM customer_master WHERE store_id=? AND customer_name=? AND customer_phone=?",
    storeId, name, phone);
if (!existing.isEmpty()) {
    return Result.success(customerRepo.findById(existing.get(0).get("customer_id")).orElse(null));
}
```

### 4.2 重复请求
关键操作（如支付、退款）建议前端去抖 + 后端幂等键。

## 5. 总结清单

| 项 | 规则 |
|---|------|
| 写操作 | 必须 `@Transactional` |
| 跨表写 | 必须同事务 |
| 异常 | try-catch 内必须 `setRollbackOnly()` |
| 高冲突资源 | 使用 `FOR UPDATE` 悲观锁 |
| 删除 | 禁止 DELETE，用 `is_active=0` |
| 删除前 | 必须留审计日志 |
| 创建接口 | 关键资源必须幂等 |
| 唯一约束 | 数据库层兜底 |
