## 三、并发幂等测试做法与结果

- 做法：8 线程 + `CountDownLatch`（ready/go 两段栅栏）同时调用 `MarketingInquiryService.submit`，同 requestId、同载荷（同手机号/姓名/日期/人数/来源），收集 8 个回执。
- 结果：
  - 回执 id 去重后 **1 个**（8 线程返回同一 id）；
  - 回执 inquiryNo 去重后 **1 个**（8 线程返回同一 inquiryNo）；
  - `marketing_attribution_event` 该 requestId **1 行**；
  - `booking_inquiry` 该 id **1 行**。
- 结论：并发同 requestId 同载荷只产生一条咨询 + 一条事件，回执一致。

## 四、409 反例结果

- 同 requestId 不同手机号（不同载荷）→ `IllegalStateException`（控制器映射 409），零新增：该 requestId 事件仍 1 行、该手机号咨询仍 1 行。

## 五、lookup 四态结果

- 正例（正确 inquiryNo + phone）→ 返回 inquiryNo/status=pending/expectedDate/partySize/createdAt；
- 查无（inquiryNo 不存在）→ `success(null)`；
- 电话不符 → `success(null)`；
- 非法输入（非法 inquiryNo、缺 phone）→ `success(null)`。

## 六、零半单逐项结果（全拒绝且咨询/事件行数不变）

- 暂停 sourceCode、过期 sourceCode、未来生效 sourceCode、未知 sourceCode → 均拒绝；
- 非法日期（过去日期）→ 拒绝；
- 非法人数（0）→ 拒绝；
- 缺 requestId → 拒绝；
- 断言：非法输入前后 booking_inquiry 与 marketing_attribution_event 行数一致（零半单）。

## 八、实现要点

- 并发安全：`TransactionTemplate` 事务内先插咨询、再插事件（`marketing_attribution_event.request_id` 唯一键为最终闸门）；事件插入遇唯一键冲突即回滚整个事务并回查完整载荷比对，一致返回原回执，不一致抛 IllegalStateException（409）。
- sourceCode 咨询只接受 customerName/phone/expectedDate/partySize/remark/sourceCode/requestId，服务端反查当前可见发布取得 publicationId/storeId/channel，忽略客户端 storeId，不默认门店 1。
- legacy（无 sourceCode）继续兼容原字段，storeId 必须合法正数，缺门店不兜底 1。
- inquiryNo 稳定为 `INQ` + id；lookupUrl 固定 `/h5/inquiry/{inquiryNo}`；重放返回完全相同值。
- 回查双因子（inquiryNo + phone），查无/不符/非法统一 success(null)，禁止按手机号列举。
