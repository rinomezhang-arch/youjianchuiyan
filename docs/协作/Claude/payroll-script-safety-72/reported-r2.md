## 代码修复（真的落了，不只是测试）

`run-http-e2e.sh`：脱敏子进程是 `>(redact_stream >> "$APP_LOG")` 进程替换，
独立子 shell，退出状态天然传不回主脚本，`set -o pipefail` 管不到它——之前
`redact_stream`/`sed` 真出故障时主脚本完全无感知，会当正常继续。改为把子进程
真实退出码写进哨兵文件（`.redact-rc.$$`，留在 `$EVID` 不删除，遵守"不清理临时
证据"），启动失败分支里等子进程真正退出后读这个值，非 0 则额外报"脱敏器故障"，
不当作已处理。

## 如实交代：自动化验证这次没做干净，不装作做到了

先说结论：**这次的自动化测试没能给出一个我能信得过的 PASS/FAIL 信号**，
不是因为改动本身有问题，是我在这台 Windows 开发机上反复被环境问题绊住，
过程如下，全部如实列出：

1. `env-precheck.sh` 顶部写死 `EXPECTED_HOSTNAME="VM-0-14-ubuntu"`——
   这是机身校验，伪造它等于假装自己是那台生产旁路机器，**这个我不会伪造**。
   所以不能像卡里字面意思那样从脚本最开头整个跑一遍，只能定向抽取我改动的
   那一段真实代码（`awk` 原样抽取，不是重写）单独执行。
2. 第一次用 `python -c` 做字符串替换时，中文文本在这台机器 GBK 控制台下显示
   乱码，导致我以为文件被污染，浪费了一轮排查——后来证实那只是终端渲染问题，
   文件内容本身没坏，改用 Edit 工具精确匹配后正常。
3. 第一次搭 stub PATH 时，把 `C:/Users/...` 直接塞进 `PATH` 环境变量，
   bash 把 `C:` 里那个冒号当成了 PATH 分隔符，导致我的桩目录整个失效，
   `mysql` 命令悄悄落到了真的系统 mysql 上。改成 POSIX 风格 `/c/Users/...` 后修正。
4. 搭好桩后第一次真跑通了"抽取的真实代码段"，**哨兵文件机制本身被直接证实有效**：
   人工检查过 `.redact-rc.*` 文件内容确实精确等于我模拟的 `sed` 桩的退出码 `7`，
   说明"子进程真实退出码能被捕获"这个核心机制是对的。
5. 但那次跑出来的整体判定不可信——测试哈内斯自己漏定义了 `$DB_HOST`/`$SCHEMA`
   等变量，被抽取代码段里引用到时在 `set -u` 下直接把整段代码提前打断退出，
   根本没跑到我新加的检测逻辑那一步，之前的"PASS"是假阳性。修了变量缺失后
   重跑，这次整个哈内斯直接挂死超时，没有任何输出。
6. 到这里已经远超卡内"一次聚焦测试失败最多一次定向修复"的额度，我选择停下
   如实报告，而不是继续加码硬凑一个自动化绿灯。

**能负责任地说的是**：哨兵文件捕获真实退出码这个核心机制，我用人工检查
（不是自动化断言）证实过一次是对的；代码改动本身逻辑自洽、通过了肉眼审查
（kill 真实子进程 → wait 其真正退出 → 此时管道关闭 → redact_stream 子 shell
