## 漏洞（已复现，证据在 UI-08 reported-2）

`POST /api/booking-inquiries/{id}/convert` 只校验「桌台属于**咨询**所在门店」，
**从未校验调用者自身的门店与角色**。二店员工用二店 JWT，把一店的咨询转成了一店的正式预订并占了一店的桌台。

## 三条约束，必须同时满足

统筹点名两条，我加一条自己的：

1. **未授权的幂等重放也不得泄露 `bookingId`。**
   现在的重放分支在任何门店校验之前就把原单号还回去了——
   越权者只要拿对 id，即使转不了单，也能白拿一个真实单号，
   而那个单号加上手机号就能查到客人的行程。所以**权限校验必须早于重放返回**。
2. **不能破坏并发只生成一单。**
   咨询行的排他锁必须仍是本事务**第一条数据库语句**：
   普通查询会先建立一致性读快照，后到事务带着过期快照进来就会建出第二张单。
3. **权限校验需要咨询的 `store_id`，而它来自被锁的那一行。**

三条合起来只有一种顺序成立：

```
锁咨询行 FOR UPDATE        <- 仍是第一条数据库语句，并发不受影响
  -> 用锁到的 store_id 做门店与角色校验   <- 早于重放返回，越权者拿不到单号
  -> 重放判定 / 新建
```

## 验证

真实 JWT + 隔离 MySQL，覆盖：越权转单被拒且零副作用、**越权重放不泄露单号**、
