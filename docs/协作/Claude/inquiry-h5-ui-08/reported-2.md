## 只登记不修：后端 convert 缺门店与角色校验 —— **复现成立**

统筹的怀疑属实，**已在隔离库复现，未改任何后端代码**。

**复现步骤**（隔离 schema `e2e_ui08_1788853545`）：

1. 建二店员工 `e2e-manager2`（`store_id=2`），真实登录拿到 JWT（193 字符）。
2. 用**二店**的 token 调 `POST /api/booking-inquiries/2/convert`，
   目标是**一店**的咨询 id=2，桌台用**一店**的 11。
3. 真实响应：`{"code":200,"bookingId":"BK17888545887361e6ee","tableIds":[11]}` —— **成功了**。
4. 数据库回读：该单 `store_id = 1`，二店员工凭空生成了一张一店的正式预订。

**根因**：`convert` 只校验了「桌台属于**咨询**所在门店」，
**从未校验调用者自身的门店与角色**。

**旁证，强度更高**：同一控制器的 `GET /api/booking-inquiries` 明确要求
`can_manage_hr = 1`（第 327-331 行），而 `convert` 连登录之外的任何检查都没有。
**相邻两个端点权限强度不一致**，写的时候多半是漏了，不是有意放宽。

**影响范围**：任何持有合法员工 JWT 的人都能把任意门店的咨询转成正式预订并占用该店桌台。
不需要越权凭证，只要能登录。

**我没有修**——越界改后端不在本任务边界内。建议统筹另立任务，
口径建议与 `ReceivablePaymentService.requireStore` 一致：无身份拒绝、非总经理不得跨店。
