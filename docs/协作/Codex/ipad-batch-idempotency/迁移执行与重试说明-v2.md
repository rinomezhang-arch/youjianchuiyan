# 迁移执行与重试说明

本说明是父后续在授权目标执行的操作顺序。本轮仅对独立localhost测试实例执行，未对生产执行。迁移资源：banquet_project/src/main/resources/ipad_batch_request_migration_v2.sql。两条ALTER不是幂等脚本、不是整体事务；禁止以BEGIN/ROLLBACK承诺原子回退。

## 0. 只读核验
确认当前DATABASE为本次授权目标；v1收据表已存在。仅检查这两张表，不遍历/清理生产目录或其他库。

```sql
SELECT DATABASE(), @@SESSION.foreign_key_checks;
SHOW CREATE TABLE booking_master;
SHOW CREATE TABLE ipad_batch_request;
SELECT TABLE_NAME,COLUMN_NAME,COLUMN_TYPE,CHARACTER_SET_NAME,COLLATION_NAME
FROM information_schema.COLUMNS
WHERE TABLE_SCHEMA=DATABASE()
  AND TABLE_NAME IN ('booking_master','ipad_batch_request')
  AND COLUMN_NAME IN ('id','booking_master_id','store_id','booking_id');
SELECT TABLE_NAME,INDEX_NAME,NON_UNIQUE,INDEX_TYPE,
       GROUP_CONCAT(COLUMN_NAME ORDER BY SEQ_IN_INDEX) AS ordered_columns,
       COUNT(*) AS column_count,SUM(SUB_PART IS NOT NULL) AS prefix_columns
FROM information_schema.STATISTICS
WHERE TABLE_SCHEMA=DATABASE()
  AND TABLE_NAME IN ('booking_master','ipad_batch_request')
GROUP BY TABLE_NAME,INDEX_NAME,NON_UNIQUE,INDEX_TYPE;
SELECT CONSTRAINT_NAME,ORDINAL_POSITION,COLUMN_NAME,
       REFERENCED_TABLE_SCHEMA,REFERENCED_TABLE_NAME,REFERENCED_COLUMN_NAME
FROM information_schema.KEY_COLUMN_USAGE
WHERE CONSTRAINT_SCHEMA=DATABASE() AND TABLE_NAME='ipad_batch_request'
  AND REFERENCED_TABLE_NAME IS NOT NULL
ORDER BY CONSTRAINT_NAME,ORDINAL_POSITION;
SELECT CONSTRAINT_NAME,UPDATE_RULE,DELETE_RULE
FROM information_schema.REFERENTIAL_CONSTRAINTS
WHERE CONSTRAINT_SCHEMA=DATABASE() AND TABLE_NAME='ipad_batch_request';
SELECT COUNT(*) AS scope_mismatches
FROM ipad_batch_request r LEFT JOIN booking_master b
  ON b.id=r.booking_master_id AND b.store_id=r.store_id AND b.booking_id=r.booking_id
WHERE b.id IS NULL;
```

必须满足：foreign_key_checks=1；对应列实际类型/signedness及字符串charset/collation相容（本候选验收为signed BIGINT与VARCHAR255 utf8mb4_0900_ai_ci）；scope_mismatches=0。列结构不同、同名不同定义、脏关系非0均先停止并登记交父，不能自动转换或改数据。预检与DDL之间可能发生并发变化，预检0不代替ALTER的实际验证。

父表需要完整三列UNIQUE BTREE，顺序id,store_id,booking_id，column_count=3、prefix_columns=0。主键id虽在逻辑上使三元组唯一，但本迁移需要完整三列索引支持标准复合引用；单列booking_id唯一也不满足引用列序。已有同定义索引时核验并复用，跳过第一条，不能盲加重复；同名但定义不同则停止。

## 1. 按现存结构执行缺失步骤

| 查明状态 | 执行 |
| --- | --- |
| 无三列唯一、无复合FK，且预检合格 | 先资源STEP 1，检查成功，再STEP 2 |
| 三列唯一已存在且定义正确、无复合FK | 跳过STEP 1，仅STEP 2 |
| 索引及完整复合FK均已存在且定义正确 | 不执行ALTER，只核验历史收据和下述最终状态 |
| 第二步失败 | 立即停止；重新查索引/FK/列/关系状态，记录错误码及已生效阶段 |
| 发现脏关系或collation问题 | 不重试数据写入，不关闭FK，不删除/修改记录；交父决定另项处理 |
| 同名索引/FK定义不符 | 停止；不DROP/重命名/重建去掩盖差异 |

最终复合FK必须是同库booking_master，列对应依次booking_master_id→id、store_id→store_id、booking_id→booking_id；ON UPDATE/DELETE RESTRICT。原fk_ipad_batch_booking仍需存在。若已有等效不同名称的结构，不擅自加冗余约束，先登记实际名称给父确认纳入迁移状态。

SQL资源本身不含自动分支，操作者/既有迁移工具必须按上述只读结果选择资源中标记的STEP；不能给整个文件加“忽略错误继续”来伪造幂等成功。没有新迁移管理配置或自动启动逻辑。

## 2. 部分完成与保留证据

第一条ALTER成功即可能已提交；第二条遇脏关系1452或不兼容collation3780失败，不会撤销第一条。不能用事务rollback或失败退出码推断“什么都没改”。此时保存SHOW CREATE TABLE/索引/FK结果，确认第一步是否生效、第二步是否不存在，保留全部原收据。已知脏数据未有另项授权处理前停止；不要反复尝试相同失败迁移。测试中的重复第二步只为证明仍拒绝、没有隐性修复。

本轮实证：dirty隔离库保留3份收据（2份真实历史副本+1份有意错店副本），两次第二步1452，三列父索引仍在、复合FK不存在，行快照不变。collation隔离库保留2历史副本，第二步3780，索引仍在、FK不存在、collation未改。它们是独立负例证据库，不要拿来当成功迁移基线，不做清理。

## 3. 完成验收

重复第0节结构查询确认精确列序/索引全列/两条FK/foreign_key_checks/0错配。对迁移前记录的正确历史主单、收据、菜行逐行比较，不能只数空表或只看DDL成功。

本轮先保留两店真实业务历史再迁移，迁移后原核心11语义复跑通过，并增加3项迁移测试；父整合后复跑专属IpadBatchScopeFkMysqlTest即可。旧IpadBatchIdempotencyMysqlTest中的v1缺口负例只适用于无v2的隔离夹具，不能将其“错配被接受”的旧断言用于已迁移schema；新子类同名override在v2下明确断言拒绝，原文件/证据冻结。

本项只补齐收据三列到真实主单的关系，JSON内部内容及员工关系未新增数据库约束。生产发布、前端和安全receipt读取不属于本增量执行范围。
