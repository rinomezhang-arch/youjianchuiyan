## 1. P1：设备未绑定员工时，直接信任X-Staff-Id

**精确证据**：`banquet_project/src/main/java/com/youjian/banquet/config/IpadInterceptor.java:63-79`。读取请求头员工号；查询active设备绑定后，只有boundStaffId非空才比较员工；第79行在绑定为空时将requestedStaffId写入ipad_staff_id。没有验证该员工存在、属于本店、在职或完成登录。`frontend_v3/src/api/ipad.js:17-20`从本地状态发送四个头；`frontend_v3/src/store/ipad.js:10`的SN来自localStorage或时间戳，不是硬件身份凭证。

**合成复现**：独立实例创建active设备`SYN-IPAD-AUTH-01`，绑定store_id=1、staff_id=NULL；创建本店开放订单SYN-ORDER-01及菜品SYN-DISH-01；员工900001故意不存在。不调用login/verify，发送：

```http
POST /api/ipad/order/dish/add
Content-Type: application/json
X-Client-Type: ipad
X-Device-Sn: SYN-IPAD-AUTH-01
X-Store-Id: 1
X-Staff-Id: 900001

{"booking_id":"SYN-ORDER-01","dish_id":"SYN-DISH-01","dish_quantity":1}
```

验证点：真实拦截器是否放行并设置ipad_staff_id=900001；业务最终成功与否还受实体外键等约束，**不能预先断言一定写库成功**。可在隔离测试Handler中观察属性，避免业务其他校验掩盖身份缺口。IpadOrderController.java:105-106仅检查属性员工号为有效整数，不验证员工真实性。

**影响**：空绑定设备把客户端输入提升为受信任操作人；SN可复制不能证明设备持有者。已绑定员工分支虽比对数字，也不等价于员工登录凭据。

**最小修复建议**：空员工绑定仅允许受限登录入口；其他业务必须消费服务端认证员工会话，验证同店、在职、有效期。保留设备门店校验但不要以SN充当秘密；无需改变法务或PC全局权限配置。

## 2. P1：授权校验无可验证回执，批量加菜可伪造body.staff_id

**精确证据**：`controller/IpadOrderController.java:251-286`校验本店账号密码后只返回staff_id/name/role，未签发授权token或写服务端可消费记录。`同文件:320-325`直接解析body.staff_id，无必填、同店员工、授权回执校验；`:378`把其用于通知senderId。订单锁和同店菜品校验仍存在，不能误报为缺少订单门店隔离。`frontend_v3/src/views/ipad/order/GuestOrder.vue:329-351`先verify再传verifiedStaff.staff_id只是客户端顺序，没有凭据与批量提交绑定。

**合成复现**：设备正常绑定合成员工101和门店1，有上述本店订单/菜品；不请求auth/verify，直接提交：

```http
POST /api/ipad/order/add-dishes
Content-Type: application/json
X-Client-Type: ipad
X-Device-Sn: SYN-IPAD-BOUND-01
X-Store-Id: 1
X-Staff-Id: 101

{"booking_id":"SYN-ORDER-01","staff_id":900002,"dishes":[{"dish_id":"SYN-DISH-01","dish_quantity":1}]}
```

再用另一份独立合成订单省略body.staff_id。断言未完成verify时应拒绝且订单明细不变；源码目前没有相应拒绝步骤。隔离通知捕获应检查是否出现伪造senderId=900002或NULL；不能以消息发送失败推断授权已被拦截。

**影响**：绕过预期人工授权步骤、通知署名可伪造；不应把body.staff_id称为授权token。单靠前端弹出密码框无法建立服务端授权链。

**最小修复建议**：验证成功后产生短期、可消费的授权ID或签名凭据，绑定设备/门店/员工/订单/操作目的；批量提交服务端核验有效期并消费或幂等记录，员工身份从凭据取而不是body取。先明确共享设备换班流程，不能将设备永久绑死某个人。

## 3. P1：退菜接口仅检查同店明细，无授权回执或操作权限校验

**精确证据**：`controller/IpadOrderController.java:473-499`的实际路由是`/order/dish/refund`；校验原因、同店明细和未退状态后直接置refunded，未校验已授权员工/权限/token。`:484-486`有同店过滤，不能误报为任意跨店退菜。`frontend_v3/src/api/ipad.js:60`导出ipadOrderRefund；本轮在views/ipad检索未找到该函数调用方，不伪造“前端已执行授权”的结论。

**合成复现**：正常active绑定设备，创建本店未退菜明细700001（其订单未付款，仅合成业务），不调用verify：

```http
POST /api/ipad/order/dish/refund

X-Client-Type: ipad
X-Device-Sn: SYN-IPAD-BOUND-01
X-Store-Id: 1

```

验证点：没有授权时是否仍置refunded；复现前后比对明细状态与授权审计，不向真实订单发送。此接口源码是**退菜状态操作**，不是银行退款执行；是否需要经理二次授权需秋哥确认，不能编造已批准的角色制度。

**影响与最小修复**：当前设备门店匹配即可到达退菜状态变更，无法证明经过规定员工审批。先明确可退菜角色/场景，再在服务端使用与第2项一致的可验证授权凭据或真实员工会话校验权限，保留现有同店过滤和重复退菜保护；不得凭body或请求头自称经理。
