# IPAD-AUTH-CHAIN-02 前后端契约（候选，待Java回归）

## 前端 → 后端

所有iPad请求仍需active设备及同店X-Device-Sn/X-Store-Id/X-Client-Type，X-Staff-Id可为0；设备SN不等于强身份。

1. POST /api/ipad/auth/verify：`{username,password,booking_id}`。真实同店在职员工密码核验及同店开放订单验证。成功Result.code=200，data包含authorization_token（43字符随机不透明票据）、expires_in=120、booking_id、purpose=ipad:batch-add，以及仅展示用staff_id/staff_name/role。
2. POST /api/ipad/order/add-dishes：`{booking_id,authorization_token,dishes:[{dish_id,dish_quantity}]}`。不接受body.staff_id。服务端消费票据得到员工；设备/店/订单/用途必须匹配，员工仍在职。同票据仅一次消费；失败不产生本次订单写入。令牌消费后的业务失败也要重新授权。
3. 现有Result封装保持：控制器拒绝通常HTTP200且code=400/403/503；拦截器拒绝为HTTP401/403。前端须检查code，不把HTTP200当业务成功。

GuestOrder只在内存持有票据，授权完成清票据和密码，不写localStorage；忙碌时拒第二次授权。网络未知保留购物车并提示先核对订单，不自动重试。这不是批量业务幂等；重新授权后人为重复提交仍可能新增，应另做业务幂等而非假称票据解决所有重复。

## 共享设备与边界

精确POST login/verify/batch不依赖头员工身份；login仍由现有真实密码验证后更新绑定，实现换班。空staff绑定的其他业务写入拒绝。精确菜单GET允许客人浏览，不扩成全部GET。order/detail虽已有前端调用，但当前读取源码没有对应控制器映射；本轮只保留路径许可，不能声称原订单详情缺失已修复。

票据服务内存上限10000，签发回收过期记录，120秒；不使用PC/法务JWT密钥或持久配置。重启清空，跨实例没有共享票据，需同实例请求或重新授权；不同节点失败关闭。未引入共享缓存/数据库迁移/配置更改，发布前父代理须确认实例路由。本轮不改变经理/退款角色制度；既有绑定员工分支仍依赖设备记录+匹配头，不能宣称整个iPad已成为强会话鉴权。

## 共享设备与失败恢复复核补充

- 换班通过现有login真实密码验证更新设备绑定，仍只允许active同店设备；新拦截器不再要求旧员工头匹配才允许login。凭据签发不更改绑定，客人当次确认可由另一位同店在职员工完成，不赋予经理角色。
- 票据原子消费早于原有订单写入，保证同票据并发最多一个进入业务。业务校验失败/事务失败/进程重启后的票据不能恢复，需要再次核验。业务响应丢失时不得自动重新授权并重发，应先核对订单；该轮未实现业务幂等。
- 未消费票据在换班后仍可在120秒内被同一设备使用，身份仍为当次密码核验员工；消费时复核在职与门店。换班是否应撤销已授权操作没有既有明确制度，本轮不擅自设定，记录供父评审。
- 原6项旧缺口刻画测试将先快照保存到个人证据，再按父授权改为新拒绝合同；必须在父57回归结束后执行，当前原源码未改。
