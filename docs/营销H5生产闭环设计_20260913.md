# 营销发布与客人 H5 生产闭环

设计读法：这是面向又见炊烟客人的移动 H5，使用现有深绿、柔白和克制金色品牌语言；重点是可信活动、真实门店和快速咨询，不做模板化营销页。设计参数为 `DESIGN_VARIANCE=6`、`MOTION_INTENSITY=4`、`VISUAL_DENSITY=3`。

## 一、现状与生产缺口

当前 `marketing_activity` 只能保存活动基本字段，没有审批状态、发布版本、渠道、公开地址和不可变来源码。`MarketingController` 创建活动时缺门店会默认写门店 1，更新时允许改门店，删除接口会物理删除活动。后台营销页的多张快捷卡片又跳回营销总览，没有活动编辑、审批、发布或 H5 预览流程。客人 H5 没有公开活动列表和详情，`booking_inquiry` 也没有保存营销来源。

因此现有“活动”只能作为内部资料，不能证明广告已发布，也不能把咨询、预订、到店和收入追到某次发布。

## 二、唯一业务流程

状态按以下顺序流转：

`draft -> pending_approval -> approved -> published -> paused / expired`

驳回回到 `draft` 并保留审批记录。取消使用 `cancelled` 状态，不提供物理删除接口。已发布活动不能原地改公开内容；编辑会生成下一版本草稿，旧版本继续公开，直到新版本通过审批并发布。暂停只停止公开展示，历史发布和来源码永久保留。

张晓秋和张婧使用既有审批权限批复。权限依据实时登录身份和权限码，客户端姓名只显示，不参与授权。门店员工只能看本店；总经理创建活动时必须明确选择门店，服务端不得默认门店 1。

## 三、最小数据模型

### 1. `marketing_activity` 作为活动主单

保留现有表，候选迁移增加：

| 字段 | 用途 |
|---|---|
| `status varchar(24)` | 唯一权威状态 |
| `document_version int` | 当前编辑版本，初始 1 |
| `row_version bigint` | 乐观锁，防止两人互相覆盖 |
| `created_by bigint`、`updated_by bigint` | 从实时身份取得 |
| `submitted_at`、`approved_at` | 流程时间 |

`store_id` 保持非空并去掉默认 1。`is_active` 仅在过渡期兼容读取，不能继续与 `status` 双写成两个权威状态。活动一旦产生发布记录，不允许修改 `store_id` 或 `activity_code`。

### 2. `marketing_publication` 作为不可变发布版本

| 字段 | 用途 |
|---|---|
| `publication_id bigint` | 内部主键 |
| `activity_id bigint`、`store_id bigint` | 同店关联活动 |
| `version int` | 发布版本 |
| `channel varchar(24)` | `h5`、`wecom` 等明确渠道 |
| `public_slug varchar(80)` | H5 地址标识，全局唯一 |
| `source_code varchar(64)` | 不可变转化来源码，全局唯一 |
| `title`、`summary`、`content_json` | 发布时的公开内容快照 |
| `hero_asset_url`、`cta_label` | 公开素材和行动按钮 |
| `status varchar(20)` | `published`、`paused`、`expired` |
| `valid_from`、`valid_to` | 带时区的公开有效期 |
| `published_by`、`published_at`、`paused_by`、`paused_at` | 执行人和时间 |
| `request_id varchar(64)` | 发布幂等键 |

唯一键：`(activity_id, version, channel)`、`public_slug`、`source_code`、`request_id`。索引至少覆盖 `(store_id,status,valid_from,valid_to)`。发布行不更新内容快照；暂停只改变执行状态并留下执行人和时间。

### 3. `marketing_attribution_event` 作为转化事件

| 字段 | 用途 |
|---|---|
| `event_id bigint` | 主键 |
| `publication_id`、`store_id`、`source_code` | 关联发布版本和门店 |
| `event_type varchar(24)` | `view`、`inquiry`、`booking`、`arrival`、`settlement` |
| `visitor_key varchar(64)` | 浏览器匿名标识的哈希，不存明文隐私 |
| `business_type`、`business_id`、`business_no` | 咨询、预订或结算来源 |
| `amount decimal(12,2)` | 仅结算事件使用 |
| `request_id varchar(64)` | 客户端重试幂等键 |
| `occurred_at`、`created_at` | 事件时间 |

唯一键 `request_id`；索引覆盖 `(publication_id,event_type,occurred_at)`、`(store_id,event_type,occurred_at)` 和 `(business_type,business_id)`。所有事件必须与发布记录同店。

`booking_inquiry` 增加可空的 `marketing_publication_id`、`source_code`、`source_channel`。客人提交时服务端用 `source_code` 反查有效发布并取得门店，不能信任客户端另传的门店。咨询转正式预订已有唯一 `booking_id`，后续收入通过 `booking_inquiry.booking_id -> booking_master -> settlement` 回查，不在首版重复改 `booking_master`。

## 四、接口契约

内部接口：

- `POST /api/marketing/activities`：创建草稿。门店范围用户从身份取门店；跨店总经理必须传合法 `storeId`。
- `PUT /api/marketing/activities/{id}`：仅草稿可改，必须传 `expectedRowVersion`；门店和活动编码不可改。
- `POST /api/marketing/activities/{id}/submit`：绑定 `business_type=marketing_activity`、业务主键、业务单号和 `document_version` 进入既有审批流。
- `POST /api/marketing/activities/{id}/publish`：只接受已批准的同一版本；必须带 `channel`、公开内容和 `requestId`，事务内创建不可变发布行。
- `POST /api/marketing/publications/{id}/pause`：暂停公开展示，重复请求返回原结果。
- 原 `DELETE /activities/{id}` 改为状态取消；已有发布记录时不允许取消历史。

公开接口：

- `GET /api/public/marketing/activities?storeId=...`：只返回 `published` 且当前处于有效期内的公开字段。
- `GET /api/public/marketing/a/{publicSlug}`：返回单个公开快照；草稿、未审批、暂停、过期和跨店内容统一不公开。
- `POST /api/public/marketing/events`：记录脱敏浏览事件，`requestId` 幂等。
- `POST /api/public/booking-inquiry`：允许附 `sourceCode`；服务端验证发布状态和有效期后写入来源字段，并生成 `inquiry` 事件。

公开响应不包含预算、成本、操作人、审批备注、内部规则或其他门店经营数据。

## 五、页面与使用方式

### 后台营销工作台

页面顶部只保留三个直接动作：`新建活动`、`待我审批`、`查看已发布 H5`。主体按草稿、待审批、已发布、已结束分栏，活动行直接显示门店、有效期、当前版本、渠道和状态。新建或编辑使用三步侧滑窗：基本信息、客人页面、审批与发布。每一步都自动保存草稿并显示最后保存时间；发布前必须打开真实 H5 预览。

物理删除按钮取消。暂停、复制为新活动、创建新版本和查看转化数据各有明确入口。加载用与内容同形的骨架；空状态提供“新建活动”；保存错误留在对应字段下；网络失败不能弹“发布成功”。

### 客人 H5

首屏在手机初始视口内显示门店、活动标题、有效期、真实门店照片和唯一主按钮“咨询档期”。页面依次展示活动内容、适用套餐或菜品、使用规则、门店地址与电话，再给一次同名行动按钮。使用现有深绿为主体、金色只用于主按钮和有效期提示，避免大面积金色、玻璃拟态和自动轮播。

路由为 `/h5/activity/:publicSlug`。按钮文字保持单行；图片使用现有真实门店资产并声明尺寸，移动端不横向滚动。动画只用于轻微进入和按压反馈，遵循减少动画设置。过期、暂停、未找到、网络错误各有独立页面，不能把空数据渲染成“暂无优惠”后仍允许提交。

咨询成功页显示可回查的咨询编号和查询入口。分享链接保留不可变 `sourceCode`，H5 不展示内部 ID。

## 六、端到端验收

同一候选提交和同一构建产物上完成：

1. 张晓秋创建宁国店草稿，张婧批准，发布 H5；草稿和待审批阶段公开接口均为不可见。
2. 客人从发布链接打开活动，真实页面展示正确门店、内容和有效期；记录一次幂等 `view`。
3. 客人提交咨询，刷新后能凭查询入口回读；数据库中的咨询、发布和门店一致。
4. 前台将咨询转为预订，结账后转化报表能从发布版本点回咨询、预订和结算，金额一致。
5. 重复发布、重复事件和重复咨询请求只产生一份业务结果；跨店来源码、过期来源码和暂停活动拒绝且零半成品。
6. 修改已发布活动会产生新版本；旧来源码仍指向旧快照，不被覆盖。暂停后公开接口不可见，历史归因仍可查。
7. 数据库检查孤儿、跨店、无来源发布、重复 `request_id` 和状态时间矛盾均为 0。

实体、HTTP、浏览器、网络记录和数据库回读分别保存精确通过、失败和未覆盖数字。物理渠道投放或企微发送未实际执行时必须标未覆盖，不能用 H5 页面成功代替。

## 七、实施顺序

1. 后端先提交幂等迁移、状态机、公开只读接口和来源写入，使用隔离 MySQL 验证。
2. 前端再实现后台三步窗和客人 H5，复用现有 Vue 3、Element Plus、站点照片和品牌变量，不新增 UI 框架。
3. 独立执行者在真实浏览器中跑发布、查看、咨询、转预订、暂停和归因链，检查孤儿及跨店。
4. 统筹验收后才纳入发布候选；生产迁移、部署和外部渠道发送另走最终发布批准。

法务模块、法务数据、法务配置和张律师权限始终不在本设计与实施范围内。
